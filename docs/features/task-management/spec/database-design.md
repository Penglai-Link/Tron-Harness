# Database Design: Task Management

## Database Decision

- status: approved
- impact: rebuild legacy task schema for the superpower enum contract and remove backend task seed data
- approved_by: clouds3n
- approved_at: 2026-05-19

## Existing Schema Impact

Task management continues to read existing `workspaces` and workspace effective users through service validation. No workspace, user, role, auth, or variable tables are changed by this slice. Only task tables and their SQLite bootstrap path change.

## Proposed Schema

### tasks

- change_type: create-or-recreate
- fields: `id`, `task_code`, `workspace_code`, `parent_task_code`, `title`, `description`, `status`, `previous_status`, `priority`, `task_type`, `source_type`, `source_url`, `progress_value`, `created_at`, `updated_at`, `archived_at`
- constraints:
  - unique `task_code`
  - `status` check constrained to the final superpower status enum
  - `previous_status` check constrained to active statuses only
  - `priority` check constrained to `Low`, `Medium`, `High`
  - `task_type` check constrained to `Feature`, `Bug`
  - `progress_value` between 0 and 100
- indexes: `workspace_code/status`, `parent_task_code`
- notes: `taskCode` remains generated by the backend and used by frontend navigation.

### task_user_assignments

- change_type: recreate-if-legacy-reset
- fields: `id`, `task_code`, `user_code`, `assigned_at`
- constraints: unique `task_code` and `user_code`
- indexes: `task_code`, `user_code`
- notes: effective-user validation happens in the application service against workspace-management.

### task_agent_links

- change_type: recreate-if-legacy-reset
- fields: `id`, `task_code`, `agent_code`, `linked_at`
- constraints: unique `task_code` and `agent_code`
- indexes: `task_code`
- notes: agent codes remain opaque string links in this slice.

### task_app_links

- change_type: recreate-if-legacy-reset
- fields: `id`, `task_code`, `app_code`, `linked_at`
- constraints: unique `task_code` and `app_code`
- indexes: `task_code`
- notes: app codes remain opaque string links in this slice.

## Relationships And Cardinality

One Active workspace owns many tasks. One task can have zero or one parent task and many direct child tasks. Parent and child tasks must share one workspace. One task can have many assigned users, many agent string links, and many app string links.

## Migration Plan

- Update the base task migration SQL to the final `Feature | Bug` and superpower status enum contract.
- Add one development-stage reset SQL batch for legacy task schema rebuild.
- The repository does not track applied migrations, so the reset must run only when legacy task schema is detected. Detection is based on the existing SQLite table definition still containing old task enum values.
- When legacy schema is detected, the reset batch drops `task_user_assignments`, `task_agent_links`, `task_app_links`, and `tasks`, then recreates them under the final contract. This intentionally deletes historical backend task data.
- Remove backend task seed creation so new and reset databases start empty.

## Query And Performance Plan

Primary queries still filter by workspace, status, search, priority, parent task, and assignee. Kanban reads derive columns from backend status enums. Detail reads assemble one task with assigned users, integration string links, parent summary, and active direct child summaries. Role-based status validation happens in application code, not in SQL.

## Data Governance

Task APIs require authentication. Workspace and user references remain stable external codes. Delete remains out of scope; archive/restore is still the lifecycle boundary for inactive tasks. Feature evolution explicitly permits task-history reset during development for this slice only.

## Test Data And Fixtures

Backend no longer seeds starter task rows. API tests create only the rows they need in isolated SQLite database paths. Frontend mock/demo data remains available and is updated to the new status and type model.

## Validation Commands

- `rtk make be-test`: validates conditional legacy reset behavior, persistence, route contracts, and role-based status rules.
- `rtk make be-check`: validates Rust compilation.
