# Feature Spec: Task Management

- best_practice_defaults_applied: yes
- user_confirmation_status: approved_with_defaults

Task Management v1 is a minimal full-stack planning loop. It replaces mock-only task pages with authenticated Rust APIs and React pages for workspace-scoped tasks, parent-child modeling, user assignment, kanban projection, detail reads, create/update, status changes, progress changes, and archive/restore. Execution remains a frontend Toast placeholder. Import/export stay out of scope and are not exposed from normal task navigation.

## Requirement

- user_story: Operators create and manage tasks inside a workspace, assign effective users, track status/progress, archive/restore inactive work, and inspect parent or child task detail without entering execution.
- intent: Establish the smallest persisted task-management closed loop needed by the current kanban, detail, create, update, subtask, and search pages.
- outcome: The current task pages work against backend data and keep status, priority, type, and source options aligned with backend-owned enums.

## Scope Boundary

### Assumptions

- `taskCode` is generated by the backend and is the external task identifier.
- Every task belongs to one `workspaceCode`; create requires an existing Active workspace.
- `assigneeUserCodes[]` must be effective users of the selected workspace.
- Agent and app management are not implemented in v1. `agentCodes[]` and `appCodes[]` are persisted string links without referential validation.
- Parent and child tasks must share one workspace.
- `sourceUrl` is optional and may be an empty string.
- `Completed` status forces progress to `100`.
- `Archived` is a real task status. Archive stores the previous active status; restore returns to that previous status or `Backlog`.

### In Scope

- Backend task domain, service, SQLite repository, migration, and authenticated `/api/v1/tasks/**` routes.
- Backend-owned enums:
  - `TaskStatus`: `Backlog`, `Todo`, `InProgress`, `Testing`, `Review`, `Reopen`, `Completed`, `Archived`
  - `TaskPriority`: `Low`, `Medium`, `High`
  - `TaskType`: `Feature`, `BugFix`, `Refactor`
  - `TaskSourceType`: `Internal`, `GitHub`, `GitLab`
- Task list/search, kanban projection, create, detail, PATCH update, dedicated status/progress update, archive/restore, and child creation through `parentTaskCode`.
- Frontend workspace selector driven by workspace admin APIs.
- Frontend assigned-user selection driven by workspace effective users.
- Detail status/progress controls, subtask creation, task type/source editing, assigned-user display/edit, and execution placeholder Toast.

### Out Of Scope

- Real task execution or backend execute endpoint.
- Import, export, delete, audit timeline, notification workflow.
- Agent/app management UI or referential validation.
- Global Shell workspace picker refactor.

### Constraints

- Always use existing Makefile commands for verification.
- Keep the project response envelope with `code`, `message`, and `data`.
- Do not hardcode frontend enum business logic beyond a same-value mock fallback; API mode uses `/api/v1/tasks/options`.
- Do not develop directly on `master`.
- Use shared Toast for user-visible feedback.

## Feature Model

Task is a workspace-owned aggregate with optional parent, many user assignments, many agent/app string links, backend-owned status/priority/type/source, a stored progress value, and timestamps. Direct children are read with the detail response. Archived tasks are hidden from list and kanban by default unless `includeArchived=true` is used with an archived status query.

## Page And Module Surface

- Backend: `domain::task`, `application::task`, SQLite task repository, migration, and HTTP routes under `/api/v1/tasks`.
- Frontend: `/tasks`, `/tasks/new`, and `/tasks/detail?taskCode=...`.
- Routing: board card click navigates by backend-generated `taskCode`; import/export routes and buttons are not part of v1 task navigation.
- Tests: backend API integration tests plus focused Playwright coverage for workspace selection, search, create, detail, update, subtask, archive/restore, and execution Toast.

## Repository Findings

- Existing frontend task pages were present but depended on mock data and placeholder task endpoints.
- Backend had no task domain, application service, SQLite repository, migration, route, or API tests before this feature.
- Workspace management and user management provide the required `workspaceCode` and effective-user dependencies.
- Shared Toast exists and is already used by admin pages.
- Lite Git Spec is declared by project instructions, so implementation uses branch `feature/clouds3n/task-management` and mirrored worktree path.
