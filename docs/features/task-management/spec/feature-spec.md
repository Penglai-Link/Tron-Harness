Task Management evolves from the original persisted v1 loop into a superpower-aligned status model. The feature still serves as a lightweight planning surface for workspace-scoped tasks, but status ownership is now role-aware: feature root tasks represent intention flow, feature child tasks represent execution flow, and bug tasks represent defect flow. Development-stage historical backend task data may be discarded to land the new contract cleanly.

## Scope Boundary

### Assumptions

- `taskCode` is generated by the backend and remains the external task identifier.
- Every task belongs to one `workspaceCode`; create requires an existing Active workspace.
- `assigneeUserCodes[]` must be effective users of the selected workspace.
- Agent and app management remain string-link persistence only; `agentCodes[]` and `appCodes[]` are not referentially validated in this slice.
- Parent and child tasks must share one workspace.
- Feature role is derived from `taskType` and `parentTaskCode`:
  - `Feature` with no parent is a feature root task.
  - `Feature` with a parent is a feature child task.
  - `Bug` uses the bug flow regardless of parent presence.
- Archive stores the previous active status; restore returns to the stored previous status when it is still valid for the task role, otherwise it returns the role default `Open`.
- Development-stage historical backend task data may be deleted. The backend does not need to preserve or migrate old `Backlog/Todo/Testing/BugFix/Refactor` task rows.

### In Scope

- Backend task domain, service, SQLite repository, migration/reset logic, and authenticated `/api/v1/tasks/**` routes.
- Backend-owned enums:
  - `TaskStatus`: `Open`, `Designing`, `Red`, `Green`, `Regressioning`, `Review`, `InProgress`, `Reopen`, `Completed`, `Archived`
  - `TaskPriority`: `Low`, `Medium`, `High`
  - `TaskType`: `Feature`, `Bug`
  - `TaskSourceType`: `Internal`, `GitHub`, `GitLab`
- Backend-owned task role rules:
  - feature root statuses: `Open`, `Designing`, `Red`, `Green`, `Regressioning`, `Review`, `Completed`, `Archived`
  - feature child statuses: `Open`, `InProgress`, `Completed`, `Archived`
  - bug statuses: `Open`, `InProgress`, `Completed`, `Reopen`, `Archived`
- Backend-owned default statuses:
  - feature root: `Open`
  - feature child: `Open`
  - bug: `Open`
- Task options expansion through `GET /api/v1/tasks/options` with `statusRules` and `defaultStatuses`.
- Task list/search, kanban projection, create, detail, PATCH update, status changes, archive/restore, and child creation through `parentTaskCode`.
- Development-stage backend task reset by rebuilding legacy task schema/data and removing backend seed tasks.
- Frontend minimal adaptation only:
  - create page type options become `Feature` and `Bug`
  - detail page status dropdown filters by task role
  - subtask creation defaults to the parent task type
  - board/mock/demo data adopt the new type and status contract

### Out Of Scope

- Real task execution or backend execute endpoint.
- Strict adjacent transition graph enforcement inside each role flow.
- Import, export, delete, audit timeline, notification workflow.
- Agent/app referential validation or dedicated agent/app management UI.
- Global Shell workspace picker refactor.
- Superpower orchestration details such as subagent dispatch, evidence ledger UI, or execution engine embedding inside the task pages.

### Constraints

- Always use existing Makefile commands for verification.
- Keep the project response envelope with `code`, `message`, and `data`.
- Do not hardcode frontend business rules beyond role-aware filtering that mirrors backend `statusRules`; API mode remains source of truth through `/api/v1/tasks/options`.
- Do not develop directly on `master`.
- Use shared Toast for user-visible feedback.

## Feature Model

Task remains a workspace-owned aggregate with optional parent, many user assignments, many agent/app string links, backend-owned status/priority/type/source, stored progress, and timestamps. The status model is no longer one global lifecycle; it depends on the task role inferred from `taskType` and parent presence. Active direct children are read with the detail response; archived subtasks are omitted from parent detail and subtask counts. Archived tasks are hidden from list and kanban by default unless `includeArchived=true` is used.

## Page And Module Surface

- Backend: `domain::task`, `application::task`, SQLite task repository, legacy-schema reset path, and HTTP routes under `/api/v1/tasks`.
- Frontend: `/tasks`, `/tasks/new`, and `/tasks/detail?taskCode=...`.
- Routing: board card click still navigates by backend-generated `taskCode`.
- Tests: backend API integration tests plus focused Playwright coverage for workspace selection, debounced board search, create, detail, role-filtered statuses, subtask inheritance, archive/restore, and backend reset expectations.

## Repository Findings

- Existing frontend task pages and tests already cover create, detail, subtask, archive/restore, and board behaviors, but they are still wired to the old global status list and old `BugFix`/`Refactor` types.
- Backend task persistence currently seeds old example tasks and still stores old status/type enums inside SQLite constraints.
- The repository does not have migration tracking; task schema reset must therefore be conditional and idempotent rather than an unconditional destructive SQL batch on every startup.
