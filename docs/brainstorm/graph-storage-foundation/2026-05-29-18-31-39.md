# Graph Storage Foundation Brainstorming Spec

## Context

Tron has frontend mock surfaces for knowledge graph, knowledge base, and memory. The backend has no graph, ontology, memory, or Grafeo bounded context yet. The backend follows DDD and hexagonal architecture: inbound adapters call application services, application owns ports, domain owns pure business rules, and outbound adapters implement application ports.

The latest `master` contains a temporary LLM runtime service with `embedding_call`, `embedding_call_with_chunking`, and `rerank_call`. Graph callers must not provide embeddings directly. The graph service derives embeddings internally through that runtime when a store or query operation needs vector data.

## Goal

Create a pure backend graph storage foundation for internal modules. The first version exposes Rust services and ports only. It does not add HTTP APIs, frontend pages, or frontend data-source integration.

The foundation must support two graph modes:

- LPG for business knowledge graphs: entities, relationships, structured filters, traversal, full-text search, vector search, and hybrid search.
- RDF for ontology: class, property, domain, range, constraints, and SHACL data for operations, development, test, and design ontology domains.

## Non-Goals

- No public or protected HTTP API in the first version.
- No frontend integration for the existing knowledge graph or knowledge base pages.
- No raw GQL, Cypher, SPARQL, or Grafeo query strings accepted from internal callers.
- No separate Grafeo database file per namespace in the first version.
- No `inheritable` field or equivalent persistence flag on graph records.
- No caller-supplied embedding vectors as the normal API contract.
- No dependency on Grafeo server or enterprise-only runtime features.

## Confirmed Decisions

- Use one embedded Grafeo catalog.
- Map `namespace` to a Grafeo schema.
- Map the root workspace code to a Grafeo named graph.
- Store `workspaceCode`, `appCode`, and `userCode` as required Grafeo properties on every node and edge.
- Normalize missing `appCode` or `userCode` to the sentinel string `__NONE__` before writing Grafeo properties. Do not write null graph attributes.
- Resolve embeddings inside the graph application service by calling `LlmRuntimeService::embedding_call` or `embedding_call_with_chunking`.
- Keep the first version backend-internal. Internal modules use Rust services and ports.

## Approaches Considered

### Recommended: Internal Graph Service With Grafeo Adapter

Add a new `graph` bounded context. Domain types describe graph scope, records, ontology resources, search, and traversal. Application services define `GraphStore` and `OntologyStore` ports and own scope resolution, embedding calls, validation, and query planning. The outbound Grafeo adapter implements the ports.

This matches the current backend architecture and keeps Grafeo replaceable.

### Alternative: Direct Grafeo Adapter Used By Callers

Expose a thin Grafeo wrapper and let each module build its own graph queries. This is faster to scaffold but would duplicate scope rules, embedding logic, sentinel normalization, and ontology behavior. It also makes isolation bugs likely.

Rejected.

### Alternative: HTTP-First Graph API

Add `/api/v1/graph` routes now and let frontend and backend share one API. This is useful later, but it expands the first slice beyond the stated internal backend need.

Rejected for the first version.

## Architecture

Use this module shape:

```text
tron-backend/src/
  domain.rs
  domain/
    graph.rs
    graph/
      scope.rs
      lpg.rs
      ontology.rs
      query.rs
      error.rs

  application.rs
  application/
    graph.rs
    graph/
      dto.rs
      port.rs
      service.rs
      scope_resolver.rs
      embedding.rs

  adapters/
    outbound.rs
    outbound/
      graph.rs
      graph/
        grafeo.rs
        query_mapping.rs
        ontology_mapping.rs
```

No `mod.rs` files should be added.

`GraphService` composes:

- `WorkspaceService` to validate workspace status and resolve workspace lineage.
- `LlmRuntimeService` to derive embeddings for vector-indexed writes and vector clauses in search.
- `GraphStore` for LPG persistence and retrieval.
- `OntologyStore` for RDF ontology persistence and retrieval.

`GraphStore` and `OntologyStore` are application ports. Grafeo is only an outbound adapter.

## Scope Model

`GraphScope` contains:

- `namespace`: required domain namespace; maps to Grafeo schema.
- `workspaceCode`: required current workspace.
- `appCode`: optional app boundary.
- `userCode`: optional user boundary.

`ScopeResolver` derives:

- `rootWorkspaceCode`: the first item in the workspace path; maps to Grafeo named graph.
- `visibleWorkspaceCodes`: the current workspace path from root to current workspace.
- `storedAppCode`: `appCode` or `__NONE__`.
- `storedUserCode`: `userCode` or `__NONE__`.

All writes target the resolved named graph for the root workspace and store the exact current `workspaceCode`.

All reads are limited to one named graph. A query can see records whose `workspaceCode` is in `visibleWorkspaceCodes`, and whose app/user dimensions match the requested filters. No query crosses root workspace named graphs.

## Grafeo Mapping

Use this physical shape:

```text
catalog
  schema: namespace
    named graph: rootWorkspaceCode
      nodes
      edges
      labels
      indexes
      MVCC
```

Required node and edge properties:

- `namespace`
- `workspaceCode`
- `appCode`
- `userCode`
- `createdAt`
- `updatedAt`

`namespace` is stored redundantly on records even though it maps to schema. This supports diagnostics and future export/import paths.

The Grafeo adapter creates single-value indexes for `workspaceCode`, `appCode`, and `userCode`. It may add label, external ID, full-text, vector, and ontology indexes where Grafeo supports them.

## LPG Contract

Core records:

- `GraphNode`: stable node code, labels, dynamic properties, optional text fields for full-text and embedding.
- `GraphEdge`: stable edge code, source node code, target node code, label, dynamic properties, optional text fields.
- `GraphSearchQuery`: structured filters, full-text text, vector text, labels, traversal seed, limit, and score options.
- `GraphTraverseQuery`: start node, edge labels, direction, max depth, filters, and limit.

The domain model stores dynamic properties as typed values, but adapter mapping must normalize missing isolation values to `__NONE__`. It must not emit nulls for isolation dimensions.

## Ontology Contract

Core ontology records:

- `OntologyClass`
- `OntologyProperty`
- `OntologyDomain`
- `OntologyRange`
- `OntologyConstraint`
- `ShaclShape`

Ontology records use RDF mode in Grafeo and the same scope resolution as LPG. Ontology domains include operations, development, test, and design. The service should allow namespaces to define more ontology domains later.

## Embedding And Hybrid Search

Callers provide text, not vectors.

For writes:

- If a node or edge requests vector indexing, `GraphService` calls `LlmRuntimeService::embedding_call`.
- If content exceeds the configured chunk threshold, `GraphService` calls `embedding_call_with_chunking` and stores chunk vectors as adapter-supported vector records.
- The embedding call uses the current `workspaceCode` and optional model override from graph command metadata.

For reads:

- If `GraphSearchQuery` includes vector text, `GraphService` derives the query vector through `embedding_call`.
- If no vector text is present, the service skips embedding and runs structured, full-text, or traversal-only search.
- If vector search is requested and no embedding model is available, the service returns a graph embedding error. It must not silently run a weaker query.

Hybrid search combines:

- structured filters
- full-text search
- vector search
- graph traversal
- optional rerank in a later slice through `LlmRuntimeService::rerank_call`

## Error Handling

Use stable domain errors such as:

- `NamespaceRequired`
- `WorkspaceRequired`
- `InvalidWorkspace`
- `InvalidScope`
- `NodeNotFound`
- `EdgeNotFound`
- `DuplicateNode`
- `DuplicateEdge`
- `OntologyResourceNotFound`
- `EmbeddingUnavailable`
- `EmbeddingProviderFailed`
- `StorageFailure`

Because the first version has no HTTP API, these errors do not need HTTP mapping yet. Future HTTP adapters must use the existing `ApiResponse` envelope.

## Testing Strategy

Use Makefile targets first:

- `rtk make be-check`
- `rtk make be-test`

Recommended proof areas:

- Unit tests for scope resolution, root workspace named graph selection, lineage visibility, and sentinel normalization.
- Unit tests proving no `inheritable` field exists in graph domain records or adapter payloads.
- Service tests proving store/search calls derive embeddings through `LlmRuntimeService` instead of requiring caller vectors.
- Adapter contract tests proving Grafeo keys are generated from catalog/schema/named graph/scope.
- Integration tests for LPG node/edge CRUD, traversal, structured filtering, full-text search, vector search, and hybrid search.
- Integration tests for ontology class/property/domain/range/SHACL CRUD.

## Implementation Notes

- Reuse existing `WorkspaceService` lineage behavior instead of duplicating workspace tree traversal.
- Keep Grafeo APIs behind the application ports. Domain and application code must not depend on Grafeo concrete types.
- Store `__NONE__` only at the adapter/persistence boundary. Public Rust command DTOs should keep optional `appCode` and `userCode`.
- Keep the graph service async where embedding calls are involved.
- If Grafeo's Rust crate API differs from assumptions, adapt only the outbound adapter and preserve the `GraphStore` and `OntologyStore` contracts.

## Open Risks

- Grafeo embedded APIs and crate packaging must be verified during implementation. Network access to crates.io failed during the design scan, so implementation must confirm the exact crate name, feature flags, and API.
- Vector index and chunk storage shape may need adjustment to match Grafeo's embedded API.
- Rerank belongs to a later slice unless search quality requires it before graph consumers can use the service.
