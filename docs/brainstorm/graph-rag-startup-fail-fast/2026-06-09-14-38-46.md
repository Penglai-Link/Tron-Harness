# Graph RAG Startup Fail Fast

## Summary

This fix makes graph and RAG startup behavior explicit on the `release/0.1.0` line.
Graph and RAG are treated as backend hard dependencies. If either dependency cannot
initialize at startup, the backend must fail before binding the HTTP listener.

To avoid mixing process liveness with dependency readiness, `/api/v1/health`
continues to report static process metadata only, while a new
`/api/v1/readiness` endpoint reports whether hard dependencies are ready to
serve traffic.

## Problem

The backend currently initializes graph core and RAG storage eagerly during app
bootstrap, but readiness semantics are implicit:

- startup uses `expect(...)` and crashes on dependency initialization failure
- `/api/v1/health` still returns a static `ok` payload
- tests and docs do not define the intended fail-fast contract

This creates a semantic mismatch between bootstrap behavior and health
reporting.

## Decision

Use split semantics:

- `/api/v1/health`: liveness only
- `/api/v1/readiness`: hard dependency readiness
- app bootstrap: returns explicit startup errors instead of panicking through
  `expect(...)`

## Scope

In scope:

- explicit app bootstrap error type for graph and RAG startup failures
- router/bootstrap refactor from infallible constructors to `Result`
- new readiness endpoint with the standard response envelope
- backend contract coverage for startup failure and readiness semantics

Out of scope:

- changing non-graph non-RAG startup warnings into hard failures
- provider-network readiness checks
- unrelated graph `OnceLock` lifetime/cross-instance cleanup

## API Contract

### GET `/api/v1/health`

- returns `200`
- returns the existing success envelope
- reports only safe static metadata

### GET `/api/v1/readiness`

- returns `200` with `status=ready` when hard dependencies are ready
- returns `503` with `status=not_ready` when hard dependencies are unavailable
- keeps the standard response body shape
- reports safe component-level status only, without leaking paths, secrets, SQL,
  or internal stack details

## Implementation Notes

- convert `AppState::new` to `Result<AppState, AppBootstrapError>`
- convert `build_router` to `Result<Router, AppBootstrapError>`
- replace graph/RAG bootstrap `expect(...)` calls with explicit error mapping
- store a lightweight readiness snapshot in app state so the readiness handler
  does not rebuild dependencies

## Verification

- `make be-check`
- `make be-test`
- focused contract coverage for:
  - invalid graph storage path fails startup
  - invalid RAG storage initialization fails startup
  - `/api/v1/health` contract remains stable
  - `/api/v1/readiness` returns `200` or `503` with the standard envelope
