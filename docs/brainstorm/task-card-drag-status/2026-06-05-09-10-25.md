# Task Card Drag Status Brainstorm

## Context

- User selected a task card on `/tasks` and requested drag-and-drop status updates across kanban status columns.
- Current backend already exposes `POST /api/v1/tasks/{taskCode}/status` and applies role-aware status validation.
- Current task board renders status columns and clickable cards, but has no drag/drop interaction.

## Confirmed Decisions

- Use the existing backend status endpoint with `POST`.
- Kanban drag/drop sends only `{ status }`; it does not send `progress`.
- Backend remains authoritative for status validation and progress behavior. `Completed` forces progress to `100`; other states preserve existing progress when no progress value is provided.
- Frontend should prevent obvious invalid drops by mirroring `/api/v1/tasks/options.statusRules`, then still rely on backend errors as final truth.
- Native HTML5 drag/drop is preferred over adding a dependency.

## Chosen Approach

Add draggable task cards and droppable kanban columns to the existing task board. Keep click-to-detail behavior intact. On valid cross-column drop, optimistically move the card, call `POST /api/v1/tasks/{taskCode}/status`, refresh board data on success, and restore the previous board state on failure.

## Alternatives Considered

- Add a dedicated DnD library: better touch support, but larger scope and dependency churn for a desktop-first board.
- Add a new pathless status endpoint: better matches the latest API convention, but the user explicitly chose the existing endpoint.
- Enforce adjacent transitions in the frontend: rejected because the backend intentionally supports cross-status changes within each task role.
