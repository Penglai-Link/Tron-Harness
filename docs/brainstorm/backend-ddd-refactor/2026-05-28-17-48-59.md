# Backend DDD Refactor Spec

## Context

The backend already follows a DDD and hexagonal shape at the top level:
`domain`, `application`, `adapters/inbound`, and `adapters/outbound`.
The current problem is that several bounded contexts still concentrate too
many responsibilities in one large Rust file, especially application services
and SQLite adapters.

The repository spec in `tron-backend/docs/spec/rust-coding-spec.md` fixes the
dependency direction:

- `adapters/inbound -> application -> domain`
- `adapters/outbound -> application ports`

The same spec requires context root files to be facades and forbids new
`mod.rs` module roots.

## Goal

Refactor backend modules toward the documented DDD layout without changing
business behavior, API contracts, persistence schema, route paths, response
envelopes, or test expectations.

## Scope

The first refactor batch targets the largest responsibility buckets:

- `tron-backend/src/application/model/service.rs`
- `tron-backend/src/application/skill/service.rs`
- `tron-backend/src/application/user/service.rs`
- `tron-backend/src/application/workspace/service.rs`
- selected large outbound adapter files that implement application ports

The preferred order is:

1. Split application services by use-case support concept, DTO, port, and
   cohesive helper modules while preserving facade exports.
2. Split outbound SQLite adapters by schema/bootstrap, row mapping, query, and
   command helpers where this reduces file concentration.
3. Strengthen architecture tests only where they verify the project rule, not
   merely the current implementation.

## Design Rules

- Keep context root files as small facade modules.
- Do not add `mod.rs`.
- Keep `domain` pure: no Axum, Rusqlite, Reqwest, API envelope, adapter, or
  application imports.
- Keep application ports in `application`, not in outbound adapters.
- Keep HTTP request/response/error mapping in inbound adapters.
- Prefer Rust-private leaf modules and controlled `pub use` exports so callers
  keep stable paths such as `crate::application::model::ModelService`.
- Split by business or adapter responsibility, not by generic buckets such as
  `utils.rs` or broad `helper.rs` when a concept-specific name is available.

## Acceptance

- `rtk make be-check` passes.
- `rtk make be-test` passes.
- No new `mod.rs` files exist.
- Existing API response envelope behavior is unchanged.
- Existing public service imports used by routes/tests still compile.
- The largest backend files are measurably smaller and no longer represent a
  whole bounded context in a single implementation file.

## Non-Goals

- No route, DTO, database schema, migration, or frontend contract changes.
- No behavior rewrite of model, skill, user, workspace, task, automation, or
  auth features.
- No cleanup of unrelated warning noise unless it blocks verification.
