# Variable Sensitive Data Brainstorm

## Context

Tron variable management currently treats every variable value as ordinary text.

- Backend persistence stores `workspace_variables.variable_value` and `platform_variables.variable_value` as plaintext.
- Variable list APIs return `value` directly.
- Frontend workspace and platform variable pages render `value` in tables, detail panes, edit forms, and search.
- Agent invocation reads the same variable catalog and puts values into `AgentRunContext.variables`.

Task 636177 changes this model. A variable can be marked as sensitive. Sensitive values must be encrypted at rest, masked in normal display as `********`, and revealed only after a second verification step.

## Requirement

Add sensitive value handling to platform and workspace variable management.

- Users can mark a variable as sensitive when creating or editing it.
- Sensitive values are not stored in plaintext.
- Normal variable lists, detail pages, edit forms, mocks, and browser tests do not expose sensitive plaintext.
- Page reveal requires server-side second verification.
- Runtime variable consumption keeps a separate backend-only path for plaintext resolution.
- Existing non-sensitive variables remain compatible after migration.

## Current Repo Findings

### Backend

- `domain/variable/catalog.rs` defines `Variable`, `PlatformVariable`, and `EffectiveVariable` with plaintext `value`.
- `application/variable/service.rs` and `service/use_cases.rs` expose one shared `list_variables` path used by UI and runtime.
- `adapters/outbound/persistence/sqlite/variable_repository.rs` reads and writes `variable_value` as text.
- Migrations `20260518_0009_create_variable_management_variables.sql` and `20260525_0016_create_platform_variables.sql` have no sensitive metadata columns.
- Existing auth has session and bcrypt password verification. Bcrypt is one-way and cannot encrypt variable values.

### Frontend

- `VariableManagementPage.tsx` renders workspace effective variable values directly.
- `PlatformVariablesPage.tsx`, create/edit/detail pages, and helper search code render or match `record.value` directly.
- `variableApi.ts` and `VariableModel.ts` model variable values as always visible strings.
- Mock variable data and Playwright smoke tests expect plaintext values.

### Runtime

- `AgentInvocationService` calls `VariableService::list_variables` and puts returned values into `AgentRunContext.variables`.
- `react_runtime` consumes context in-process.
- `service_mode_runtime` serializes the whole `AgentRunContext` and sends it to an external runtime endpoint.
- `system_cli_runtime` does not obviously consume variables today, but it still receives the shared context shape.

## Selected Approach

Build sensitive variables as a split-read model:

1. Display reads return masked values.
2. Reveal reads decrypt one value only after second verification.
3. Runtime reads resolve plaintext through a dedicated backend path and apply a trust policy before secrets leave the backend process.

This keeps UI safety and runtime compatibility separate. It avoids changing one shared `list_variables` method in a way that either breaks agent execution or leaks secrets to the page.

## Core Decisions

### Sensitive Flag

Add `isSensitive` to platform and workspace variable create/edit flows.

- New variables default to non-sensitive unless the user enables the option.
- Inherited sensitive variables stay sensitive in effective workspace display.
- A workspace override of a sensitive inherited key must remain sensitive. The product must not let a child workspace silently downgrade an inherited secret key into plaintext storage.

### Storage Encryption

Use Rust national crypto through `gmcrypto-core` with the `sm4-aead` feature and `SM4-GCM`.

- Do not hand-write an encryption mode.
- Do not use bcrypt because it cannot decrypt.
- Do not use frontend encryption because the backend and runtime still need controlled plaintext access.
- Pin the crate version during implementation after a small API spike. As of the PRD date, `gmcrypto-core 0.8.0` exposes opt-in SM4-GCM/SM4-CCM APIs behind `sm4-aead`.

Sensitive storage uses:

- `variable_value`: base64 ciphertext for sensitive rows, plaintext for non-sensitive rows.
- `is_sensitive`: boolean flag.
- `value_nonce`: base64 nonce.
- `value_tag`: base64 authentication tag.
- `value_algorithm`: `SM4_GCM`.
- `value_key_version`: key version used for encryption.

SM4 uses a 128-bit key. Configuration should carry base64 key material and an active key version. Production must provide this through deployment secrets or config injection. Tests can use a fixed test key.

### Authenticated Context

Use GCM additional authenticated data to bind ciphertext to its record identity.

Examples:

- `tron-variable:v1:platform:OPENAI_API_KEY`
- `tron-variable:v1:workspace:TRON_CORE:OPENAI_API_KEY`

If someone copies ciphertext, nonce, and tag from one variable record to another, decrypt fails because the record identity no longer matches the authenticated data.

Record identity changes affect AAD. Renaming a variable key or moving a stored secret across scopes must be implemented as decrypt old record with old AAD, then re-encrypt new record with new AAD. The backend must not update key/scope columns for sensitive rows without re-encrypting.

### Display Contract

Sensitive rows return masked values by default:

```json
{
  "key": "OPENAI_API_KEY",
  "value": "********",
  "isSensitive": true,
  "valueMasked": true,
  "hasValue": true
}
```

Normal display APIs must not return sensitive plaintext. Search must not match sensitive plaintext. It can search key, description, source labels, workspace names, and non-sensitive values.

### Reveal Contract

Reveal is a separate operation.

- User enters the current account password in a second verification dialog.
- Backend verifies the password for the current session user.
- Backend returns a short-lived step-up token. This verification does not create, refresh, or replace the login session.
- Reveal endpoints accept the step-up token and return one plaintext value for one key.
- Frontend keeps the plaintext only in the current component state and hides it when the dialog/panel closes, the workspace changes, or the page refreshes.

OAuth-only users without a local password cannot reveal in v1. They receive a stable "second verification unavailable" response until a separate OAuth re-auth design exists.

### Edit Contract

Sensitive edit forms must not prefill plaintext.

- Existing sensitive value is shown as `********`.
- Saving without a new value preserves the encrypted value.
- Replacing a sensitive value encrypts the new value.
- Changing from sensitive to non-sensitive requires a new value. The backend must not silently decrypt the old secret and write it back as plaintext.

### Runtime Contract

Create a dedicated runtime resolution path.

- UI list/detail path: masked, no decrypt.
- Reveal path: decrypt one value after second verification.
- Runtime path: decrypt only for backend-controlled execution paths that are trusted to receive plaintext.

`react_runtime` can use decrypted values because it runs in-process. `service_mode_runtime` must not receive sensitive plaintext by default because it posts `AgentRunContext` to an external endpoint. It needs an explicit trusted-runtime configuration before the backend includes sensitive plaintext.

The v1 default is fail closed: if a service-mode runtime is not explicitly trusted for secret delivery and the resolved variable set contains sensitive values, agent invocation preparation fails with a stable runtime configuration error. The backend must not send `********` as a runtime value because an agent could treat the mask as the real secret.

This keeps the v1 boundary honest: encrypted storage does not protect a value after the backend sends it to an untrusted runtime.

## API Direction

All API responses keep the existing envelope:

```json
{
  "code": "SUCCESS",
  "message": "success",
  "data": {}
}
```

New endpoints should follow the frontend/backend consensus rules:

- §2.2: use `GET` or `POST` only.
- §2.3: use kebab-case URLs and no path parameters.
- §2.4: use dedicated request bodies when more than two fields are needed.
- §2.5: use dedicated response VOs and keep extensions inside `data`.

The existing variable CRUD endpoints are legacy REST/path-parameter endpoints. This feature should not rewrite them as a hidden scope expansion. If compatibility is kept, add sensitive fields to existing request/response models carefully and create new consensus-compliant endpoints for reveal and step-up.

Recommended new endpoints:

- `POST /api/v1/auth/verify-step-up-password`
- `POST /api/v1/variables/reveal-workspace-variable`
- `POST /api/v1/admin/platform/variables/reveal-platform-variable`

Recommended step-up request body:

```json
{
  "password": "current-password"
}
```

Recommended step-up response data:

```json
{
  "stepUpToken": "short-lived-token",
  "expiresAt": "2026-06-02T17:30:00+08:00"
}
```

Recommended reveal request body:

```json
{
  "workspaceCode": "TRON_CORE",
  "variableKey": "OPENAI_API_KEY",
  "stepUpToken": "short-lived-token"
}
```

Platform reveal omits `workspaceCode`.

Create requests add `isSensitive`. Update requests must distinguish preserving a stored value from replacing it:

```json
{
  "key": "OPENAI_API_KEY",
  "description": "OpenAI key",
  "isSensitive": true,
  "valueMode": "PRESERVE"
}
```

`valueMode=REPLACE` requires `value`. Creating a variable requires `value`. Changing a sensitive variable to non-sensitive also requires `value` so the backend never decrypts an old secret and silently stores it as plaintext.

## Data Flow

### Create Sensitive Variable

1. Frontend sends key, value, description, and `isSensitive=true`.
2. Backend validates key, scope, inheritance rules, and encryption config.
3. Backend generates a nonce.
4. Backend encrypts value with `SM4-GCM`.
5. Backend stores ciphertext, nonce, tag, algorithm, key version, and sensitive flag.
6. Backend returns masked display data.

### List Variables

1. Backend loads platform/workspace variables.
2. Backend resolves inheritance and shadowing.
3. Backend returns plaintext value only for non-sensitive rows.
4. Backend returns `********` for sensitive rows.

### Reveal Variable

1. Frontend opens second verification dialog for one selected sensitive row.
2. Frontend posts the password to the step-up endpoint.
3. Backend verifies password for the current session user and returns a short-lived token.
4. Frontend posts the token and selected variable identity to the reveal endpoint.
5. Backend checks variable scope and permission.
6. Backend decrypts one value.
7. Frontend displays the plaintext temporarily and can hide it again.

### Runtime Resolution

1. Agent invocation asks for runtime variables through a dedicated method.
2. Backend decrypts sensitive variables only when the target runtime policy allows it.
3. In-process runtime can receive plaintext; external service-mode runtime can receive plaintext only when explicitly configured as trusted for secret delivery.
4. Untrusted service-mode runtime preparation fails if sensitive variables would be required.
5. Backend does not reuse display-list responses for runtime.
6. Logs, events, errors, and test output must not include plaintext secret values.

## Alternatives Considered

### Frontend Mask Only

Rejected. It hides values visually but leaves database rows, API responses, browser state, and logs vulnerable.

### Reuse Login Endpoint For Reveal

Rejected. It couples reveal to full login/session refresh behavior. A purpose-specific step-up endpoint is clearer and easier to limit.

### XChaCha20Poly1305 Or AES-GCM

Rejected for this task after the national-crypto requirement. Both are valid general-purpose AEAD choices, but they do not satisfy the requested Rust national-standard algorithm direction.

### Raw SM4 Or SM4-CBC Plus Manual MAC

Rejected. Raw block-cipher usage and manual encryption/MAC composition are easy to get wrong. `SM4-GCM` gives authenticated encryption through a library API.

### Always Decrypt For Runtime

Rejected as a default. It would keep current runtime behavior but leak sensitive values to external service-mode runtimes. The runtime path must apply trust policy.

## Scope Boundary

### In Scope

- Platform variable sensitive option.
- Workspace variable sensitive option.
- Database migration for sensitive metadata.
- SM4-GCM encryption wrapper and config.
- Masked list/detail/search behavior.
- Step-up verification for reveal.
- Single-value reveal APIs.
- Edit/preserve/replace behavior for sensitive values.
- Runtime resolver split with explicit trust boundary.
- Backend, frontend, mock, and Playwright contract updates.

### Out Of Scope

- Re-encrypting all existing plaintext variables automatically.
- OAuth provider re-auth for reveal.
- Full API style migration away from existing legacy variable routes.
- Secret-reference redesign for all runtimes.
- Agent/tool-level declared variable allowlists.
- Enterprise key-management integration.
- Audit-log product surface, unless the implementation already has a suitable append-only audit sink.

## Testing Direction

- Backend API tests prove sensitive create/list/update/reveal behavior.
- Repository tests or API tests prove sensitive database rows do not store plaintext.
- Service tests prove display reads do not decrypt and runtime reads use the dedicated path.
- Frontend tests prove tables, details, forms, and search do not expose sensitive plaintext.
- Playwright smoke proves reveal requires second verification and re-masks after closing or navigating.
- Regression tests prove non-sensitive variables still behave as before.

## Risks And Open Decisions

- Production key injection needs an environment/deployment decision. The design should not rely on a hardcoded production key.
- OAuth-only reveal is denied in v1 unless a provider-specific re-auth design is added.
- Existing legacy CRUD endpoints conflict with the stricter frontend/backend consensus. This feature should add compliant new reveal endpoints and avoid broader route migration unless approved.
- The implementation should run a small dependency spike before coding the cipher wrapper because the chosen `gmcrypto-core` SM4-GCM API is relatively new.
