# RAG 后端底座脑暴规格

## 状态

2026-05-30 已确认第一阶段范围。

## 产品输入

本轮脑暴唯一产品输入是 ONES 页面 `RAG MVP 设计方案`。

第一阶段实现 RAG 后端底座，不一次性实现全部未来能力。底座需要先支撑 Memory 和 Project Doc 的真实写入与检索，同时为 Code Graph、Summary Tree 和后续存储引擎替换留下清晰扩展点。

## 第一阶段目标

建设一个后端 RAG 底座，支持两个真实 Corpus 的写入、存储、索引、检索和上下文组装：

- `memory-card`
- `project-doc`

RAG 模块内部负责存储、Profile、写入、检索、warnings、retry 和 trace。它需要给后续模块提供稳定后端契约，但不吸收 Memory 治理逻辑、Graph 服务行为或完整权限系统。

## 已确认范围

### 后端接口

第一阶段只暴露后端 API：

- `POST /api/v1/rag/ingest`
- `POST /api/v1/rag/search`
- 只读 debug API
- 单 Source 索引重试 API

API 响应体遵循当前项目约定：

```json
{
  "code": "response status code or error code",
  "message": "error message",
  "data": {}
}
```

### 真实 Corpus

`memory-card` 和 `project-doc` 是第一阶段真实落地的 Corpus。

`code-graph` 只保留扩展位。第一阶段可以保留 enum、Profile 和 registry 扩展点，但不能启用真实代码图谱写入或图谱检索。

### 存储

第一版使用 SQLite。SQLite 是当前实现选择，不是架构边界。

每个 Corpus 使用独立物理表。需要过滤、排序或隔离的字段提升为物理列。metadata 只保存低频扩展字段。

设计需要保留 adapter 边界，后续替换存储引擎时不改变 RAG 应用层契约。

### 写入

写入使用同步可配置 DAG。

第一阶段支持这些 Stage 类型：

- source
- parse
- normalize
- split
- persist
- fulltextIndex
- vectorIndex

第一阶段优先支持纯文本和 Markdown。

调用方传入 `sourceCode` 和 `sourceVersion`。稳定键包含 corpus、scope、source code 和 source version。同版本写入使用 upsert。多个版本可以共存。

没有 `latest` 标记。如果检索请求没有传 source version 过滤条件，Retrieval Profile 必须配置固定 source version。两者都没有时，检索返回配置错误。

### 检索

检索使用固定单轮 fan-out 流程：

- 加载 Retrieval Profile
- 生成 scope filter
- 合并 Profile filters 和 Request filters
- 执行配置的 routes
- merge、dedup，并按配置 rerank
- hydrate 命中结果
- 二次校验 Source 为 active
- 组装请求的 context 格式

第一阶段支持 `memory-card` 和 `project-doc` 的全文检索与向量检索。

第一阶段支持这些 context 输出：

- `RESULT_LIST`
- `TOKEN_BUDGET_PACK`
- `MEMORY_CONTEXT_PACK`
- `DOC_QA_CONTEXT_PACK`

### Embedding

RAG 复用现有 `LlmRuntimeService`。

写入和检索 Profile 使用固定 `embeddingModelCode`。RAG 自己把内容切成 TextUnit，然后对每个 TextUnit 调用 `LlmRuntimeService::embedding_call`。第一阶段 RAG 不创建独立模型 client，也不复用 Graph 的 embedding 路径。

`project-doc` 允许向量索引失败时降级。全文索引成功时 Source 可以保持 active，同时持久化 warnings。

`memory-card` 要求 embedding 成功。embedding 失败时 Source 保持失败或不可见。

### Rerank

Rerank 是可选能力，由 Profile 控制。

启用时，Retrieval Profile 配置 `rerankEnabled`、`rerankModelCode` 和 `rerankTopN`。RAG 调用 `LlmRuntimeService::rerank_call`。失败处理遵循 Profile 的 degrade policy。

### Scope 与访问校验

RAG 使用 code 语义的标识：

- `userCode`
- `agentCode`
- `workspaceCode`

数据库行使用 `scope_type` 和 `scope_code`。

HTTP handler 从认证上下文得到当前用户，并校验用户有 workspace 访问权。RAG 自身只做 USER、AGENT、SPACE 数据隔离。RAG 不实现 corpus 权限、source 权限、repo 权限、角色权限、字段权限或内容脱敏。

### Memory 治理字段

RAG 存储 Memory 治理字段，用于过滤、排序和 hydrate。RAG 不执行 Memory 治理状态流转。

核心物理列包括：

- `memory_type`
- `memory_status`
- `review_status`
- `version`
- `superseded_by`
- `conflict_group`
- `duplicate_group`
- `injectable`
- `importance_score`
- `confidence_score`
- `quality_score`
- `pin_level`
- `expires_at`
- `derived_source_type`
- `derived_source_code`

长尾治理细节保存在 metadata，例如 review reason、quality gate detail、conflict detail、duplicate detail、derived trace、reviewer code 和 audit hints。

### Profile 与策略注册表

Profile 存储在 SQLite 中。Rust 代码持有有限策略注册表。

Profile 只能引用已注册的 strategy ID，不能执行用户自定义代码。

### Warnings、Retry、Trace 与 Events

ingest 和 indexing warnings 需要持久化，并在即时响应中返回。

search trace 使用轻量落库。它保存 query text、route counts、timings、warnings、candidate references、result count 和 token usage。它不保存 hydrate 正文、context pack body、embedding、provider 原始响应或 API keys。trace 数据 TTL 为 7 天。

retry API 针对一个 Source 和指定索引阶段重试。它不重新执行 parse、normalize 或 split，而是基于已持久化 TextUnit 重建全文索引和 embedding/vector 索引。

RAG 通过 EventBus 发送 ingest、search、retry、stage 和 route 生命周期事件。事件 payload 只包含 codes、counts、durations、warnings 和 errors。

## 明确不做

第一阶段不实现：

- 代码图谱写入
- 真实 `GRAPH` retriever 调用
- 与当前内部 `GraphService` 集成
- SummaryTree 构建
- 复杂多跳检索
- agentic retrieval
- Profile 管理 UI
- 完整权限或角色系统
- 内容脱敏
- Elasticsearch、Neo4j、PostgreSQL、pgvector、Qdrant 或 Milvus adapter
- latest 版本语义
- Memory 治理状态流转

## Graph Service 决策

最近提交已经加入内部 Graph service，提供 node、edge、traversal、hybrid graph search、scope、ontology 和 Graph 侧 embedding 能力。

这个服务适合后续 `code-graph` corpus。它不属于本次第一阶段，因为已确认 MVP 范围不实现代码图谱。

本阶段约束：

- RAG 不依赖 `GraphService`。
- `GRAPH` retriever 保持 reserved。
- `code-graph` 保持 reserved。
- SummaryTree 和 Graph 扩展点可以作为 enum 或 registry 占位存在，但不能引入运行时耦合。

后续实现 `code-graph` 时，推荐让 RAG 的 `code-graph` corpus 适配内部 Graph service，而不是在 RAG 内重复实现一套图存储。

## 设计理由

这个边界让第一阶段既有实际价值，又保持可控。Memory 和 Project Doc 现在就需要 RAG 存储与检索。Code Graph 和 SummaryTree 有独立领域行为，适合在底座稳定后再接入。

设计优先保证后端契约清晰、Profile 配置明确、写入幂等、诊断信息可持久化、存储 adapter 可替换。
