# RAG Backend Foundation Brainstorming Spec

## Status

Approved for first-phase scope on 2026-05-30.

## Product Input

The only product input for this brainstorming pass is the ONES page named `RAG MVP 设计方案`.

The first phase implements the backend RAG foundation. It does not implement every future RAG capability. The foundation must support Memory and Project Doc use cases now, while leaving clean extension points for Code Graph, Summary Tree, and future storage engines.

## First-Phase Goal

Build a backend RAG foundation that can ingest, store, index, search, and assemble context from two real corpora:

- `memory-card`
- `project-doc`

The foundation must provide stable backend contracts for later modules. It must keep storage, profile, ingest, retrieval, warnings, retry, and trace concerns inside the RAG module. It must not absorb Memory governance logic, Graph service behavior, or a full authorization system.

## Confirmed Scope

### Backend Surface

The first phase exposes backend APIs only:

- `POST /api/v1/rag/ingest`
- `POST /api/v1/rag/search`
- read-only debug APIs
- single-source indexing retry API

The API response body follows the repository contract:

```json
{
  "code": "response status code or error code",
  "message": "error message",
  "data": {}
}
```

### Real Corpora

`memory-card` and `project-doc` are real first-phase corpora.

`code-graph` stays reserved. The first phase may keep enum, profile, and registry extension points, but it must not enable real code graph ingest or graph search.

### Storage

The first implementation uses SQLite. SQLite is an implementation choice, not the architecture boundary.

Each corpus uses independent physical tables. Filterable fields become physical columns. Metadata stores low-frequency extension fields only.

The design keeps adapter boundaries so later storage engines can replace SQLite without changing application-level RAG contracts.

### Ingest

Ingest uses a synchronous configurable DAG.

The first phase supports these stage categories:

- source
- parse
- normalize
- split
- persist
- fulltextIndex
- vectorIndex

Text and Markdown are the first supported content shapes.

The caller supplies `sourceCode` and `sourceVersion`. The stable key includes corpus, scope, source code, and source version. Same-version writes use upsert. Multiple versions may coexist.

There is no `latest` marker. If a search request does not pass a source version filter, the Retrieval Profile must configure a fixed source version. Missing both is a search configuration error.

### Retrieval

Search uses a fixed single-round fan-out flow:

- load Retrieval Profile
- build scope filter
- merge profile filters and request filters
- run configured routes
- merge, deduplicate, and optionally rerank
- hydrate results
- verify hydrated sources are active
- assemble the requested context format

The first phase supports full-text and vector retrieval for `memory-card` and `project-doc`.

The first phase supports these context outputs:

- `RESULT_LIST`
- `TOKEN_BUDGET_PACK`
- `MEMORY_CONTEXT_PACK`
- `DOC_QA_CONTEXT_PACK`

### Embedding

RAG reuses the existing `LlmRuntimeService`.

Retrieval and ingest profiles use fixed `embeddingModelCode` values. RAG splits content into TextUnits, then calls `LlmRuntimeService::embedding_call` for each TextUnit. RAG does not create a separate model client or use Graph's embedding path for first-phase corpora.

`project-doc` may degrade when vector indexing fails. Full-text success may still make the source active, with persisted warnings.

`memory-card` requires embedding. Embedding failure keeps the source failed or non-visible.

### Rerank

Rerank is optional and profile-controlled.

When enabled, the Retrieval Profile configures `rerankEnabled`, `rerankModelCode`, and `rerankTopN`. RAG calls `LlmRuntimeService::rerank_call`. Failure handling follows the profile degrade policy.

### Scope And Access

RAG uses code-based identifiers:

- `userCode`
- `agentCode`
- `workspaceCode`

Database rows use `scope_type` and `scope_code`.

HTTP handlers derive the current user from authentication and validate workspace access. RAG itself only enforces USER, AGENT, and SPACE data isolation. It does not implement corpus permissions, source permissions, repository permissions, role permissions, field permissions, or content desensitization.

### Memory Governance Fields

RAG stores Memory governance fields needed for filtering, sorting, and hydration. RAG does not execute Memory governance state transitions.

Core physical columns include:

- `memory_type`
- `memory_status`
- `review_status`
- `version`
- `superseded_by`
- `conflict_group`
- `duplicate_group`
- `injectable`
- `importance_score`
- `confidence_score`
- `quality_score`
- `pin_level`
- `expires_at`
- `derived_source_type`
- `derived_source_code`

Long-tail governance details stay in metadata, such as review reason, gate details, conflict details, duplicate details, derived trace, reviewer code, and audit hints.

### Profiles And Strategy Registry

Profiles are stored in SQLite. Rust code owns the finite strategy registry.

Profiles may reference registered strategy IDs only. They cannot execute user-defined code.

### Warnings, Retry, Trace, And Events

Ingest and indexing warnings are persisted and returned in immediate responses.

Search trace is lightweight. It stores query text, route counts, timings, warnings, candidate references, result count, and token usage. It does not store hydrated text, context pack body, embeddings, provider raw responses, or API keys. Trace data has a seven-day TTL.

The retry API retries indexing for one source and selected index stages. It does not rerun parse, normalize, or split. It rebuilds full-text and embedding/vector indexes from persisted TextUnits.

RAG emits EventBus events for ingest, search, retry, stage, and route lifecycle points. Event payloads contain codes, counts, durations, warnings, and errors only.

## Explicitly Out Of Scope

The first phase does not implement:

- code graph ingest
- real `GRAPH` retriever calls
- integration with the current internal `GraphService`
- SummaryTree construction
- complex multi-hop retrieval
- agentic retrieval
- Profile management UI
- full authorization or role system
- content desensitization
- Elasticsearch, Neo4j, PostgreSQL, pgvector, Qdrant, or Milvus adapters
- latest-version semantics
- Memory governance state transitions

## Graph Service Decision

Recent commits added an internal Graph service with node, edge, traversal, hybrid graph search, scope, ontology, and Graph-side embedding support.

That service is useful for a later `code-graph` corpus. It is not needed in this first RAG phase because the approved MVP scope excludes code graph implementation.

For this phase:

- RAG must not depend on `GraphService`.
- `GRAPH` retriever stays reserved.
- `code-graph` stays reserved.
- SummaryTree and Graph extension points may exist as enums or registry placeholders, but they must not introduce runtime coupling.

When the project later implements `code-graph`, the preferred direction is to adapt RAG's `code-graph` corpus to the internal Graph service rather than duplicate graph storage inside RAG.

## Design Rationale

This boundary keeps the first phase useful and bounded. Memory and Project Doc need immediate RAG storage and retrieval. Code Graph and SummaryTree need different domain behavior and can be added after the foundation is stable.

The design favors narrow backend contracts, explicit profile configuration, idempotent writes, persistent operational diagnostics, and replaceable storage adapters.
