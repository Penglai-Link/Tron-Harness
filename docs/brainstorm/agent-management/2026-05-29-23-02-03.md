# Agent Management Brainstorm

## Context

Tron already has three strong foundations that this feature should reuse instead of inventing a fourth management pattern:

- platform settings pages under `/settings/*` with a shared settings shell
- workspace-aware inheritance and effective-state resolution in models, skills, variables, and workspaces
- a backend agent runtime and invocation surface, but no persisted agent catalog or main-agent configuration

The current `/agent` surface is a chat or runtime experience, not an administration surface. The platform also has skill-registry scanning logic and workspace binding logic that are close to what startup-scanned system agents need.

## Requirement

Tron needs an agent-management feature that:

- manages both internal and system agents
- scans system-available coding agents such as `codex` and `opencode`
- lets operators review available agents in a table-oriented admin surface
- lets operators configure the platform `Main Agent` instructions and personality
- supports workspace inheritance for system-agent availability
- keeps inherited workspace rows read-only except for local enable or disable control

The final clarified scope is:

- `Main Agent` is a platform-level singleton internal agent
- `Main Agent` is not shown in workspace agent management
- workspace agent management shows only system agents
- system agents cannot be archived in v1
- inherited system agents can only be enabled or disabled in the current workspace

## Selected Approach

Build agent management as a two-surface feature:

1. a platform settings page that owns the `Main Agent` singleton and the scanned system-agent registry
2. a workspace page that shows only inherited system agents with current-workspace enable or disable overrides

The `Main Agent` becomes a required platform configuration, not a generic row in a registry table. System agents remain discovery-backed catalog entries with persisted operator policy layered on top.

This keeps v1 smaller and cleaner:

- no per-workspace `Main Agent` override graph
- no ambiguous `archive` semantics
- no local authoring of system-agent definitions
- no writes into Codex or OpenCode config files

## Alternatives Considered

### Workspace-local main agent with nearest-ancestor inheritance

Rejected. It adds the hardest part of the feature immediately:

- authoring ownership at every workspace layer
- revert-versus-archive semantics
- nearest-ancestor merge rules
- more runtime resolution work before the first useful admin page ships

### Platform-only page with no workspace agent management

Rejected. It is simpler to build, but it drops an important part of the original requirement: workspaces need a visible way to control which system agents are effective locally.

### Keep `archive` for scanned system agents

Rejected. Scanned system agents are not authored records. If an agent disappears from the machine, that is an availability fact, not an archive action. The correct v1 replacement state is `Unavailable`.

## Scope Boundary

### In Scope

- platform settings page for agent management
- workspace agent-management page for inherited system-agent availability
- startup scan of supported system agents
- manual `Scan` action to rescan supported system agents
- persisted platform `Main Agent` instructions and personality
- persisted platform system-agent enablement
- persisted workspace-local system-agent enable or disable overrides
- backend effective-state APIs
- runtime consumption of the platform `Main Agent` configuration so the main agent works everywhere

### Out Of Scope

- per-workspace `Main Agent` configuration
- archiving agents
- creating custom system-agent records
- editing scanned system-agent metadata
- writing to external Codex or OpenCode config files
- agent-specific model overrides per system agent
- agent-specific repository or worktree execution scopes beyond current runtime behavior
- secret-reference redesign for model credentials

## Core Concepts

### Main Agent

`Main Agent` is the only internal agent in v1. It is a platform singleton with two editable fields:

- `personality`
- `instructions`

It is always available to the platform. It is not displayed in workspace agent management and does not participate in workspace enable or disable inheritance.

### System Agent

A system agent is a discovery-backed runtime capability such as `codex` or `opencode`. Its display metadata comes from backend scanning, not from manual row creation.

### Platform System-Agent Policy

The platform can globally enable or disable a discovered system agent. A platform-disabled system agent is disabled everywhere.

### Workspace System-Agent Override

A workspace can locally disable an inherited platform-enabled system agent. Re-enabling a system agent in the workspace removes the local override and returns the row to inherited platform behavior.

### Effective Workspace Agent Row

The workspace page shows effective system-agent rows only. In v1 every row is inherited from `Platform`, and the only local action is enable or disable.

## Page Surfaces

### Platform Settings Page

Route: `/settings/agents`

This page follows the existing settings-shell pattern already used by Models, Variables, and Skill Center.

The page has two sections:

1. `Main Agent` editor card
2. system-agent registry table

The `Main Agent` card shows only the human-facing editable fields:

- `Personality`
- `Instructions`

It intentionally hides redundant metadata such as `Type=Internal`, `Source=Platform`, and `Status=Enabled`.

The system-agent table shows:

- `Name`
- `Description`
- `Source`
- `Status`
- `Actions`

The page also exposes a `Scan` button above the system-agent table.

### Workspace Agent Page

Route: `/agents`

This page is a workspace-scoped capability switchboard, not a registry editor.

It shows inherited system agents only. `Main Agent` does not appear here.

The table shows:

- `Name`
- `Description`
- `Source`
- `Inherited From`
- `Status`
- `Actions`

`Inherited From` is always `Platform` in v1.

The `Type` column is intentionally removed from v1 because every visible row on both tables is a system agent, and the internal `Main Agent` is separated into its own platform editor card.

## Backend Source Of Truth

### Main Agent

Persist the `Main Agent` in a dedicated platform config store. It is not part of startup scan results and not part of workspace inheritance tables.

### System-Agent Discovery

On backend startup, Tron probes a fixed supported set of system agents such as:

- `codex`
- `opencode`

Only agents actually available on the machine become discovered catalog rows.

### Manual Rescan

The platform `Scan` button triggers a backend rescan endpoint that reruns discovery and refreshes the visible registry.

Rescan updates discovery facts only. It must not discard existing platform policy or workspace overrides for agents that remain known to Tron.

### Policy Layering

Persist operator policy separately from discovery:

- one platform policy layer for global system-agent enablement
- one workspace policy layer for current-workspace overrides

If a workspace has no local row for a system agent, it inherits the platform state.

## Status And Action Semantics

### Status

- `Enabled`: discovered and effectively enabled
- `Disabled`: discovered but turned off globally or in the current workspace
- `Unavailable`: policy exists, but the latest scan could not find the agent on the machine

`Archived` is removed from v1.

### Platform Actions

- `Main Agent`: edit and save
- system agent: `Enable`, `Disable`, `Scan`

### Workspace Actions

- inherited system agent: `Enable`, `Disable`

Workspace actions never edit metadata, never archive rows, and never affect the `Main Agent`.

### Dominance Rules

- platform disable dominates every workspace
- workspace disable only applies when the platform agent is enabled
- workspace enable removes the current-workspace local disable override
- `Unavailable` rows are read-only except for the platform `Scan` action

## API Direction

All responses use the repo-wide envelope:

```json
{
  "code": "response status code or error code",
  "message": "error message",
  "data": {}
}
```

### Platform Surface

- `GET /api/v1/agents/registry/main-agent`
- `PATCH /api/v1/agents/registry/main-agent`
- `GET /api/v1/agents/registry/system`
- `POST /api/v1/agents/registry/system/rescan`
- `POST /api/v1/agents/registry/system/{agentCode}/enable`
- `POST /api/v1/agents/registry/system/{agentCode}/disable`

### Workspace Surface

- `GET /api/v1/agents/workspaces/{workspaceCode}/system`
- `POST /api/v1/agents/workspaces/{workspaceCode}/system/{agentCode}/enable`
- `POST /api/v1/agents/workspaces/{workspaceCode}/system/{agentCode}/disable`

### Payload Direction

`Main Agent` update payload:

```json
{
  "personality": "string",
  "instructions": "string"
}
```

System-agent row payload direction:

```json
{
  "agentCode": "codex",
  "name": "Codex",
  "description": "OpenAI coding agent",
  "source": "System",
  "status": "Enabled",
  "statusDetail": null,
  "inheritedFrom": "Platform"
}
```

Workspace `inheritedFrom` is present only on the workspace surface.

## Persistence Direction

Reuse the same architectural split that skill registry already uses:

- catalog metadata for discovered items
- policy rows for workspace-effective state

Conceptual storage shape:

- `platform_main_agent_config`
  - singleton `main-agent` row with `personality`, `instructions`, timestamps
- `system_agent_registry`
  - `agent_code`, `name`, `description`, `source`, `discovered`, `last_scanned_at`, timestamps
- `system_agent_platform_policies`
  - `agent_code`, `enabled`, `updated_at`
- `workspace_system_agent_policies`
  - `workspace_code`, `agent_code`, `enabled`, `updated_at`

Even if v1 stores only workspace-local `false` rows in practice, keeping `enabled` explicit makes later expansion easier.

## Runtime Integration

This feature is not only a CRUD surface. The stored `Main Agent` configuration must become the platform source of truth used when the main agent runs.

The runtime integration direction is:

- load persisted `Main Agent` instructions and personality as part of main-agent invocation setup
- keep current model, variable, skill, and tool resolution behavior intact unless a later feature expands agent-specific runtime configuration
- do not require a workspace-local `Main Agent` record for the platform main agent to function

In v1, `Main Agent` config management and main-agent runtime consumption must ship together so the configured values actually work everywhere.

## Edge Cases

- first startup with no discovered system agents: `Main Agent` still works and the platform table renders an empty state plus `Scan`
- agent disappears after a later rescan: keep policy, mark row `Unavailable`
- agent reappears after a later rescan: restore prior policy automatically
- startup scan partially fails: app boot stays alive; the registry reports partial availability instead of crashing startup
- workspace endpoint for a missing or archived workspace: reject using the same workspace validation style already used elsewhere in the repo
- workspace cannot re-enable a platform-disabled agent into an effectively enabled state

## Implementation Notes

- reuse the existing settings-shell route conventions instead of introducing a bespoke admin container
- reuse skill-registry scanning and workspace-binding architecture where it fits
- treat `Unavailable` as a discovery state, not as a lifecycle status authored by operators
- keep v1 intentionally narrow and avoid bundling per-agent model routing, app execution policy, or secret redesign into this feature

## Validation Direction

### Backend

Focused API and service tests should prove:

- `Main Agent` get and patch behavior
- first scan inserts discovered system agents
- repeat scan preserves existing policy rows
- disappearing and reappearing agents keep their prior policies
- workspace disable and enable yield the correct effective rows
- platform disable dominates workspace state

### Frontend

Frontend proof should cover:

- `/settings/agents` loads the `Main Agent` editor and the system-agent table
- `Scan` refreshes registry state without dropping policies
- workspace `/agents` excludes `Main Agent`
- workspace toggles affect only current-workspace effective system-agent state

### Browser Proof

Browser validation is required only for the UI claims:

- settings navigation to `/settings/agents`
- `Scan` interaction feedback
- workspace page enable or disable behavior
- absence of `Main Agent` from workspace agent management

## Decision Summary

The v1 design is:

- platform-level singleton `Main Agent`
- platform settings page for `Main Agent` editing and system-agent scanning
- startup discovery plus manual rescan for system agents
- persisted platform and workspace policy layers for system-agent enablement
- workspace page that shows inherited system agents only
- `Unavailable` instead of `Archived`
- runtime consumption of the persisted `Main Agent` configuration so it works everywhere
