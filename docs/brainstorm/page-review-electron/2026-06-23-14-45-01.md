# Page Review Electron Desktop Shell

## Goal

Replace the active desktop shell implementation with Electron so Tron can support web page annotation and real page screenshots more reliably.

Keep `src-tauri` in the repository for reference and rollback. Do not delete or rewrite it in this feature. Implement Electron in a new sibling directory.

## Current Context

The existing Tauri shell in `src-tauri` owns these responsibilities:

- Start the `tron-backend` sidecar on an available local port.
- Resolve desktop data paths under `~/.tron`.
- Build and serve the bundled frontend through the backend.
- Expose desktop commands to the frontend through Tauri `invoke`.
- Check whether target pages block iframe embedding.
- Open target pages in an internal window or the system browser.
- Inject `tron-desktop-injection.js` into pages for annotation.
- Receive inspection events from target pages.

The frontend already uses `tron-frontend/src/shared/desktop/DesktopBridge.ts` as a small desktop host abstraction. That bridge should remain the main frontend integration point.

## Recommended Approach

Create a new Electron implementation under `src-electron`.

Electron should expose a frontend bridge that matches the current desktop command names:

- `desktopBackendStatus`
- `checkTargetPageEmbedding`
- `openTargetPage`
- `closeTargetPage`
- `setInjectionEnabled`
- `desktopInjectionEvent`

`DesktopBridge` should detect Electron first through `window.tronDesktop.invoke`. It should keep the current Tauri detection as compatibility fallback while `src-tauri` remains in the tree.

This keeps the page review UI stable and limits frontend changes to bridge detection, tests, and any screenshot-specific payload additions.

## Electron Structure

Use this new directory layout:

- `src-electron/package.json`
- `src-electron/package-lock.json`
- `src-electron/main/`
- `src-electron/preload/`
- `src-electron/resources/`
- `src-electron/injection/tron-desktop-injection.js`
- `src-electron/tests/`

`src-electron/injection/tron-desktop-injection.js` can start as a copy of the Tauri injection script. Later changes should happen in Electron only unless a shared injection package becomes necessary.

## Main Process Design

The Electron main process should:

- Resolve the backend sidecar binary from bundled resources.
- Pick an available backend port, starting from `TRON_BACKEND_PORT` or `8080`.
- Stop or bypass stale local `tron-backend` processes only when needed.
- Start `tron-backend` with:
  - `TRON_BACKEND_PORT`
  - `TRON_BACKEND_DATABASE_URL`
  - `TRON_BACKEND_GRAPH_STORAGE_PATH`
  - `TRON_BACKEND_FRONTEND_DIST_DIR`
- Wait for `/api/v1/health`.
- Open the main window at the backend UI once ready.
- Show a plain startup error page if the backend fails.
- Kill the managed backend process when Electron exits.

The main process should not expose Node APIs to renderer pages.

## Preload Bridge

The main app preload should expose only:

```ts
window.tronDesktop.invoke(command, payload)
```

The preload should use `contextBridge` and `ipcRenderer.invoke`. It should not expose `ipcRenderer`, `process`, or filesystem APIs.

The renderer command payload shape should stay compatible with the current Tauri bridge:

```ts
invoke("openTargetPage", { request: { url, mode, pageId } })
```

## Target Page Windows

For target pages, Electron should prefer a separate `BrowserWindow` instead of an iframe.

Each target window should:

- Use a stable page id in the window registry.
- Load only `http` and `https` URLs.
- Inject the annotation script after navigation.
- Re-inject after same-window navigation.
- Route annotation events back to the main app window.
- Handle `window.open` and target-blank navigation in the same target workflow.

When a page must open in the system browser, use Electron `shell.openExternal`.

## Screenshot Design

Electron should move screenshots from DOM-only canvas previews toward real page captures.

On `tron:node-inspected`, the target page should provide DOM metadata and element rect data. Electron should capture the page with `webContents.capturePage(rect)` when possible and attach the screenshot to the existing payload:

```ts
payload.annotationImage = {
  dataUrl,
  width,
  height
}
```

If native capture fails, fall back to the injected script's current canvas preview so the feature still returns a useful annotation image.

## Frontend Changes

Update `DesktopBridge` to:

- Detect `window.tronDesktop.invoke`.
- Keep the current Tauri invoke fallback.
- Preserve command names and response normalization.
- Add unit tests for Electron detection and fallback order.

Avoid broad changes to `TargetPageFrame` unless target-window behavior requires a small state adjustment.

## Makefile Changes

Keep the public targets:

- `make desktop-build`
- `make desktop-dev`
- `make desktop-clean`

Point them at `src-electron` instead of `src-tauri`.

`desktop-build` should:

- Run the existing integrated app build first.
- Copy frontend resources into Electron resources.
- Build the backend sidecar.
- Copy the backend binary into Electron resources.
- Run the Electron package build.

`desktop-dev` should start the same Electron shell against a local build. If the default port is busy, Electron must pick another available port and the frontend must use the matching backend URL.

## Packaging

Use Electron tooling that fits this repository's npm workflow. Prefer a minimal package setup first. Add platform packaging only after the development shell works.

Do not make `src-electron` part of the frontend workspace unless the repository needs shared workspace dependencies.

## Tests And Checks

Use Makefile entry points first.

Required checks for implementation:

- `make desktop-clean`
- `make fe-unit-test`
- `make fe-check`
- `make desktop-build` or a documented focused Electron build command if full packaging is unavailable locally

Focused checks may follow when Makefile targets are too broad:

- `npm test` or `npm run test` under `src-electron` for main-process helpers.
- Focused Vitest for `DesktopBridge`.

Manual smoke:

1. Start Electron desktop.
2. Confirm backend status reports ready.
3. Open `https://example.com`.
4. Enable annotation.
5. Select an element.
6. Confirm the inspection result includes DOM details, remark, and an image.

## Out Of Scope

- Removing `src-tauri`.
- Migrating backend APIs.
- Redesigning the page review UI.
- Persisting annotations.
- Adding OCR or image editing tools.

## Risks

- Cross-origin page behavior may differ between iframe and Electron windows.
- Injection lifecycle must handle navigation, reloads, and popups.
- Native page capture may need coordinate conversion for device scale factor.
- Packaging sidecar binaries can differ across macOS, Windows, and Linux.

## Acceptance Criteria

- A new `src-electron` implementation exists.
- `src-tauri` remains untouched except for optional comments or documentation references.
- `make desktop-dev` launches Electron, starts the backend, and opens the Tron UI.
- Frontend desktop commands work through `window.tronDesktop.invoke`.
- The existing Tauri bridge fallback remains available.
- Page annotation returns inspection data and a screenshot image.
- Target page navigation and system-browser fallback still work.
