# Tool Registry And Internal Agent Tool Exposure

## Context

Tron already has three adjacent foundations that this design should reuse instead of bypassing:

- platform settings pages under `/settings/*`
- workspace-scoped `/agents` management with existing system-agent policy controls
- backend agent runtime with concrete `EffectiveTool` schemas and in-process `ToolRegistry` execution

Repository scan also surfaced three important realities:

- current backend and frontend agent-management models only represent system agents in workspace `/agents`
- backend tests explicitly assert that `main-agent` does not appear in workspace agent rows today
- runtime authorization currently assumes one flat `AgentRunContext.tools` list that is both the allow-list and the materialized schema list

This means the request cannot be implemented as a small additive UI change. It is a feature evolution that changes workspace agent semantics, runtime tool exposure, and the boundary between code-defined tools and persisted assignment policy.

## Requirement

Tron needs a first productized tool-registry mechanism that:

- exposes a platform tools page where operators can inspect all currently available platform business tools
- turns existing backend module capabilities into executable tools
- lets workspace `/agents` manage internal-agent tool availability without removing the existing system-agent controls
- starts with one internal agent, `main-agent`
- defaults `main-agent` to all platform business tools
- lets each internal agent choose whether runtime tool exposure uses:
  - direct concrete tool list, or
  - domain discovery with on-demand expansion
- lets each internal agent choose whether an expanded domain remains available for the rest of the run
- injects the effective assigned tools into agent runtime through standard LLM tool-calling behavior

The clarified first-version boundary is:

- only platform business tools are in scope
- shell, file, grep, search, browser, and generic host-execution tools are explicitly out of scope
- tool definitions are backend-owned and code-defined, not user-authored
- system-agent CLI runtimes remain outside this new business-tool execution path in v1

## Selected Approach

Build the feature as a code-first platform tool catalog plus workspace-effective internal-agent tool policy.

The architecture has four layers:

1. `Tool Domain`
   - a discovery and organization layer such as `workspace`, `agent`, `model`
2. `Tool Definition`
   - one concrete executable business capability such as `workspace.list` or `workspace.create`
3. `Internal Agent Policy`
   - per-agent defaults plus workspace-effective overrides for exposure mode and assignment mode
4. `Runtime Materialization`
   - per-run derivation of which concrete tool schemas the model can actually call right now

The key design choices are:

- tool definitions are registered in backend code, not stored as mutable rows in the database
- persistence stores agent policy and explicit selected-tool assignments only
- `main-agent` remains the platform-defined internal agent, but workspace `/agents` evolves to show internal-agent tool policy above the existing system-agent table
- tool exposure supports both:
  - `direct_list`
  - `domain_discovery`
- domain discovery gives the model the full visible domain catalog up front as structured context and uses one discovery tool, `discovery.expand_tool_domain`, to expand concrete tools on demand

This is intentionally not the shortest path. It separates:

- tool catalog from agent policy
- assigned tools from currently materialized runtime tools
- code-defined capabilities from persisted operator overrides

That separation keeps future agent growth, tool growth, and runtime variation manageable.

## Alternatives Considered

### Put every module behind one broad `*.manage` tool

Rejected.

Examples such as `workspace.manage` or `agent.manage` create very large union-style schemas with mixed actions and mixed parameter shapes. They reduce UI count in the short term but make LLM tool selection, validation, and audit quality worse.

### Expose every concrete tool directly and never support domains

Rejected as the only model.

It works while the platform has only a handful of tools, but it scales poorly once tool count grows. The design still supports this as `direct_list`, but not as the only runtime mode.

### Use one generic `tool.invoke(toolCode, payload)` executor

Rejected.

This hides each tool's real JSON Schema from the model during actual invocation, increases malformed payload risk, and weakens auditability and future permission controls.

### Persist tool definitions and JSON Schemas in database tables

Rejected.

These tools are backend-owned code capabilities, not operator-authored content. Duplicating them in storage creates sync drift between code and catalog. The persisted source of truth should be assignments and overrides, not the definitions themselves.

### Reuse system-agent registry tables for internal tools

Rejected.

System-agent registry tracks discovered external runtimes. Business-tool registry is a code-defined internal capability catalog. Reusing the same storage model would blur two unrelated abstractions.

## Scope Boundary

### In Scope

- platform tool catalog page under the platform settings shell
- code-defined tool domain and tool definition registry
- explicit backend tool executors that wrap existing application services and use cases
- workspace `/agents` evolution to include internal-agent tool policy and assignment management
- workspace-effective policy resolution for internal agents
- runtime support for `direct_list` and `domain_discovery`
- `discovery.expand_tool_domain` tool and per-run expanded-domain state
- bootstrap default for `main-agent` to all registered platform business tools
- backend and frontend tests covering catalog, policy resolution, runtime exposure, and workspace UI behavior

### Out Of Scope

- shell, file, grep, search, browser, and host execution tools
- user-authored tool creation
- system-agent CLI runtime consuming this new business-tool registry in v1
- external plugin/MCP tool federation
- per-tool secret management redesign
- generic tool marketplace authoring flows

## Core Concepts

### Tool Domain

A discovery and grouping layer for related business tools.

V1 domain catalog fields:

- `domainCode`
- `name`
- `description`
- `toolCount`
- `sampleTools`
- `hasMutationTools`

These fields exist to help both UI and LLMs quickly understand the domain before concrete tools are expanded.

### Tool Definition

A concrete executable business capability. Tool definitions are code-defined and stable across runtime and UI.

Each tool definition should include:

- `toolCode`
- `domainCode`
- `name`
- `description`
- `operationKind`
  - `query`
  - `command`
- `inputSchema`
- `moduleOwner`
- `availabilityState`
- `sampleResultSummary`
- executor binding to an application-service use case

V1 tools should be concrete and semantically narrow enough for reliable model selection. Domain discovery solves scale, so tool definitions do not need to collapse into broad `*.manage` handlers.

### Internal Agent

An agent owned by the Tron platform itself.

V1 internal-agent surface contains only `main-agent`, but the data model must assume more internal agents will exist later.

Each internal agent has platform defaults for:

- `toolAssignmentMode`
  - `all_platform_tools`
  - `selected_tools`
- `toolExposureMode`
  - `direct_list`
  - `domain_discovery`
- `expandedDomainPersistenceMode`
  - `sticky_expanded`
  - `ephemeral_expanded`

V1 default for `main-agent`:

- `toolAssignmentMode = all_platform_tools`
- `toolExposureMode = direct_list`
- `expandedDomainPersistenceMode = sticky_expanded`

`all_platform_tools` always means all currently registered and available platform business tools at runtime resolution time. A newly added tool therefore becomes visible automatically to agents that still inherit this mode.

### Workspace Internal-Agent Policy

Workspace `/agents` is the operator surface for internal-agent tool behavior in the current workspace.

Workspace policy can override:

- assignment mode
- exposure mode
- expanded-domain persistence mode

If the effective assignment mode is `selected_tools`, the workspace can also persist explicit selected-tool assignments for that internal agent.

If `selected_tools` is active and the explicit selected set is empty, the effective assigned tool set is empty.

### Effective Tool Set

Runtime never directly trusts raw persisted assignment rows alone.

For each invocation, runtime resolves:

1. internal-agent platform defaults
2. workspace override, if present
3. explicit selected-tool assignments, if needed
4. intersection with currently registered tool definitions

The result is the run's effective assigned tool set.

## Runtime Design

Runtime must distinguish between:

- `assigned tools`
- `materialized tools currently visible to the model`

This is the critical evolution from the current flat `AgentRunContext.tools` model.

### Direct List Mode

When `toolExposureMode = direct_list`:

- runtime resolves the effective assigned tool set
- runtime materializes all assigned concrete tool schemas immediately
- runtime sends those schemas directly in the OpenAI `tools` array

This is the best mode when tool count is small.

### Domain Discovery Mode

When `toolExposureMode = domain_discovery`:

- runtime resolves the effective assigned tool set
- runtime derives the full visible domain catalog from those assigned tools
- runtime injects that full domain catalog up front as structured run context for the model
- runtime exposes only discovery tools at startup, not the concrete business tools

V1 discovery tool:

- `discovery.expand_tool_domain`

`discovery.expand_tool_domain(domainCode)` must:

- validate that the requested domain is visible to this run
- return the concrete assigned tools under that domain
- include the full JSON Schema for each returned tool
- record that domain in per-run expanded-domain state

The newly expanded concrete tools become callable only in the next model round, when runtime reissues the request with the expanded domain's concrete tool schemas added to the OpenAI `tools` array.

### Expanded Domain Persistence

When `expandedDomainPersistenceMode = sticky_expanded`:

- once a domain is expanded during a run, its concrete tools remain materialized for the rest of that run

When `expandedDomainPersistenceMode = ephemeral_expanded`:

- expanded domains do not remain permanently materialized

V1 should implement `sticky_expanded` as the default active behavior and still carry the `ephemeral_expanded` contract in data and runtime seams, even if UI keeps it disabled or labeled experimental at first.

### Runtime State Additions

Each run should carry a dedicated tool-exposure snapshot such as:

- `assignedToolCodes`
- `toolExposureMode`
- `expandedDomainPersistenceMode`
- `visibleDomainCatalog`
- `expandedDomainCodes`
- `materializedToolSchemas`

This state belongs to the run, not to global mutable process state.

### Execution Boundary

Business tools should execute through backend application services directly, not by making HTTP calls back into Tron.

That keeps:

- validation local
- transaction boundaries clear
- testing fast and deterministic
- HTTP API and tool execution aligned through shared use cases rather than self-integration loops

## Backend Architecture

To avoid name collision with the existing runtime execution `ToolRegistry`, the code should explicitly separate two concepts:

- `BusinessToolCatalog` or equivalent
  - code-defined catalog of domains, definitions, and executors
- runtime execution registry
  - current low-level executor registry that actually runs tool handlers

If the current `ToolRegistry` naming becomes ambiguous during implementation, rename the execution-layer type rather than overloading the meaning of `tool registry`.

### Suggested Module Responsibilities

- `application::tool_registry`
  - catalog assembly
  - domain listing
  - tool listing
  - tool-definition lookup
  - executor registration
- `application::agent::management`
  - internal-agent defaults
  - workspace internal-agent policy overrides
  - workspace explicit selected-tool assignments
  - effective tool-policy resolution for an agent in a workspace
- `application::agent::invocation`
  - derive effective assigned tool set
  - build runtime domain catalog
  - materialize concrete schemas according to exposure mode
- `application::agent::runtime`
  - execute concrete tools already materialized for the run

### Persistence Direction

Persist only policy and assignment rows, not tool definitions themselves.

Suggested storage groups:

- `platform_internal_agents`
  - platform defaults for internal agents
- `workspace_internal_agent_policies`
  - per-workspace override for assignment and exposure behavior
- `workspace_internal_agent_tool_assignments`
  - explicit selected tools when assignment mode is `selected_tools`

Tool definitions remain code-backed. If a persisted selected tool no longer exists in the code registry after an upgrade, it should be surfaced as stale/unavailable in management UI and ignored at runtime resolution.

## Page Surfaces

### Platform Tools Page

Route: `/settings/tools`

This follows the existing platform settings shell instead of inventing a new top-level management shell.

The page should provide:

- domain-aware search and filtering
- tool table or split view
- domain badge
- mutation/read classification
- owning module
- tool description
- JSON Schema inspection
- availability state

Because tool definitions are code-backed, this page is read-only in v1.

### Platform Agents Page

Route remains: `/settings/agents`

This page should keep its current responsibilities:

- `Main Agent` personality and instructions editor
- system-agent scan and platform enable/disable registry

V1 does not need to move tool assignment into this page. Tool-policy defaults may remain seeded or backend-managed until a future platform-level internal-agent defaults UI is needed.

### Workspace Agents Page

Route remains: `/agents`

This page evolves into two sections:

1. `Internal Agents`
2. `System Agents`

The existing system-agent table remains, preserving current workspace operator controls.

The new internal-agent section should show rows such as:

- `Name`
- `Agent Code`
- `Assignment Mode`
- `Exposure Mode`
- `Expanded Domain Persistence`
- `Assigned Tool Count`
- `Source`
  - `Platform Default`
  - `Workspace Override`
- `Actions`

Selecting an internal agent opens an editor for:

- assignment mode
- exposure mode
- expanded-domain persistence mode
- grouped tool selection by domain when `selected_tools` is active
- reset-to-platform-default action

Since v1 only has `main-agent`, the UI will often show a single row, but it must be built from scalable table/list primitives rather than a one-off hardcoded card.

## API Direction

All APIs continue to use the uniform response envelope already required by the repo.

### Tool Catalog APIs

- `GET /api/v1/tools/domains`
- `GET /api/v1/tools`
  - supports search and domain filters
- `GET /api/v1/tools/{toolCode}`

These are read-only and derive from the code-backed catalog.

### Workspace Internal-Agent APIs

- `GET /api/v1/agents/workspaces/{workspaceCode}/internal`
- `GET /api/v1/agents/workspaces/{workspaceCode}/internal/{agentCode}`
- `PATCH /api/v1/agents/workspaces/{workspaceCode}/internal/{agentCode}/policy`
- `PUT /api/v1/agents/workspaces/{workspaceCode}/internal/{agentCode}/tool-assignments`
- `POST /api/v1/agents/workspaces/{workspaceCode}/internal/{agentCode}/reset-policy`

`tool-assignments` updates replace the explicit selected set for that workspace-agent pair. They are only effective when the resulting policy mode is `selected_tools`.

### Runtime Discovery Tool Contract

`discovery.expand_tool_domain` is a runtime discovery tool, not an HTTP page-management API.

Its response should contain:

- domain metadata
- concrete visible tools under that domain
- each tool's full input JSON Schema

The runtime, not the HTTP layer, owns the expanded-domain cache and concrete materialization of those tool schemas into the next OpenAI request.

## Migration And Evolution Rules

This request reopens the earlier `agent-management` feature boundary.

Required evolution decisions:

- workspace `/agents` no longer means only system agents
- `main-agent` becomes visible in workspace agent management, but only inside the new internal-agent section
- existing backend tests that assert `main-agent` exclusion from workspace agent lists must be intentionally replaced by new internal-agent contract tests

Migration strategy:

1. add new internal-agent policy storage and code-backed tool catalog
2. keep current system-agent APIs unchanged
3. add new internal-agent workspace APIs in parallel
4. evolve frontend `/agents` to a two-section page
5. switch runtime invocation to resolve internal-agent effective tool policy when no explicit request tools are passed

This staging avoids breaking the system-agent feature while the internal-agent capability is added.

## Error Handling

The new design needs explicit typed failures for:

- unknown workspace
- unknown internal agent
- unknown domain during discovery
- domain not visible to the current agent run
- explicit selected tool no longer registered
- tool assignment payload contains duplicate or cross-domain-invalid entries
- discovery expansion requested in `direct_list` mode, if surfaced at all
- tool executor validation failure

UI should differentiate:

- stale configuration
- unavailable code-backed tool
- forbidden domain expansion
- malformed tool-assignment request

## Testing Strategy

Validation must follow the repository `Makefile` first.

Expected verification lanes:

- `make be-test`
  - catalog assembly tests
  - effective internal-agent policy resolution tests
  - stale selected-tool handling tests
  - runtime materialization tests for both `direct_list` and `domain_discovery`
  - discovery expansion tests proving schemas are returned on expansion and callable on the next round
- `make fe-check`
  - internal-agent models, page composition, forms, and filtering
- `make fe-test`
  - workspace `/agents` internal-agent assignment flow
  - system-agent regression flow still works
  - platform `/settings/tools` browsing flow

Backend tests should specifically cover the current regression seam:

- old assumption: workspace agents are system-only
- new contract: workspace page includes internal-agent section plus existing system-agent section

## Implementation Order

Recommended order:

1. separate execution-layer naming from catalog-layer naming if needed
2. add code-backed tool catalog definitions and executor registration seam
3. add internal-agent policy persistence and effective-resolution service
4. add tool catalog APIs and workspace internal-agent APIs
5. integrate runtime assigned-versus-materialized tool state
6. evolve workspace `/agents` UI and add platform `/settings/tools`
7. run Makefile-backed backend and frontend verification

This order minimizes semantic churn and prevents the UI from racing ahead of runtime truth.
