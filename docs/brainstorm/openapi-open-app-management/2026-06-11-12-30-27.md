# Tron 平台级 OpenAPI Open-App 管理与 HMAC 鉴权设计

## 背景

当前真正的 open-api 鉴权位于 `tron-backend/src/adapters/inbound/open_api/auth.rs`。

现状存在几个直接问题：

1. `Authorization: Bearer <平台 access token>` 仍可直接访问 open-api，能绕过 app 头鉴权。
2. `X-Tron-App-Id + X-Tron-App-Key + X-Tron-User-Id` 只做非空检查，没有真实 app 凭证校验。
3. `X-Tron-User-Id` 命名不准确，实际查的是 `username/email/user_code`。
4. open-api 没有平台级 open-app 管理面，也没有 appKey 轮换、停用、用户授权、API 授权能力。
5. 现有模型密钥和平台变量的 secret 处理方式以“展示遮罩”为主，不足以支撑正式的 HMAC 请求签名。

本设计用于把当前“聊天公开接口的临时鉴权”升级为“平台级开放应用机制”的第一版。

## 设计结论

第一版采用以下固定结论：

1. 只做平台级 `open-app`，管理入口只放在平台 `Settings` 下。
2. 命名统一使用 `open-app`，明确区别于现有业务 `app-management` 模块。
3. 对外正式 open-api 调用只保留 HMAC 请求签名，彻底移除 `Bearer` 调用路径。
4. 请求继续显式携带 `X-Tron-User-Code`。
5. 服务端在验签成功后，必须同时校验：
   - `open-app -> user` 是否已授权。
   - `open-app -> capability/operation` 是否已授权。
6. API 授权粒度采用“业务能力 + 操作”，不采用裸 HTTP 路径白名单。
7. 第一版 `open-app -> user` 只支持显式绑定具体用户，不支持按角色批量授权。
8. 每个 `open-app` 只有一个当前有效 `appKey`。
9. `appKey` 只在创建和轮换时明文展示一次，后续只能看到指纹或脱敏信息，不能再次查看原文。

## 目标

### 业务目标

1. 平台管理员可以在 UI 中创建和维护 `open-app`。
2. 平台管理员可以给 `open-app` 授权可代理的用户和可调用的 open-api 业务能力。
3. 外部系统可以通过标准 HMAC 签名协议调用 Tron open-api。
4. open-api 请求可以以显式指定的 `X-Tron-User-Code` 身份执行，但只能在授权范围内执行。

### 技术目标

1. 建立独立于现有 `app-management` 的平台开放应用模型。
2. 建立正式的签名、时间窗、nonce 防重放、常量时间比较机制。
3. 建立一次性 secret 展示和轮换机制。
4. 为后续新增更多 open-api 业务能力预留统一授权模型。

## 非目标

第一版不做以下能力：

1. 不做 workspace 级 open-app。
2. 不做与现有业务 `app-management` 的目录复用或模型合并。
3. 不做 OAuth2 client credentials。
4. 不做 role 级 user grant。
5. 不做并行双 key 轮换窗口。
6. 不做动态 capability 注册中心。第一版 capability 定义由代码内置，授权记录持久化。

## 范围

### In Scope

1. `Settings -> OpenAPI` 平台管理页面。
2. `open-app` 创建、列表、详情、更新、停用、启用、轮换 key。
3. `open-app -> user` 显式授权管理。
4. `open-app -> capability/operation` 授权管理。
5. 面向现有 open-api chat 能力的 HMAC 鉴权替换。
6. 现有聊天公开路由的 capability 映射和授权收敛。
7. 后端持久化、配置、测试、验收门禁。

### Out Of Scope

1. 新增第二类业务 open-api。
2. 多租户或 workspace 级 open-app 所有权。
3. 通用 SDK 发布。
4. 可视化审计中心。

## 用户与场景

### 平台管理员

1. 进入右上角平台配置，打开 `Settings -> OpenAPI`。
2. 创建 `open-app`，系统自动生成 `appId` 与一次性明文 `appKey`。
3. 记录 `appKey` 后关闭弹窗，此后 UI 只展示 key 指纹或脱敏值。
4. 给该 `open-app` 绑定允许代理的 `userCode`。
5. 给该 `open-app` 勾选允许访问的业务能力和操作。
6. 在需要时轮换 `appKey` 或停用 `open-app`。

### 外部调用方

1. 构造带 `X-Tron-App-Id`、`X-Tron-User-Code`、timestamp、nonce、signature 的请求。
2. 以 `TRON-HMAC-SHA256-V1` 规则签名。
3. 调用具体 open-api 路由。
4. 如果签名正确且 user/API 双授权通过，则以指定 `userCode` 的上下文执行。

## 命名与边界

### 新概念

- `open-app`
  - 平台级开放应用。
  - 是平台对外集成身份。
  - 不是现有 `app-management` 中的业务应用。

- `capability`
  - 对外业务 open-api 能力分类。
  - 第一版只有一个 capability：`agent-chat`。

- `operation`
  - 某个 capability 下的具体动作。
  - 例如 `session.read`、`message.write`。

### 与现有模块的边界

1. `open-app` 不复用现有 `app-management` 的 `App` 聚合。
2. `open-app` 不写入现有平台变量或模型配置表做 secret 主存储。
3. 现有 open-api chat 路由继续存在，但必须改为依赖新的 open-app 鉴权与授权上下文。

字段建议：

- `description`
- `app_id`
- `status`
- `current_key_fingerprint`

- `created_at`

2. 持有当前生效 credential 的公开摘要信息。
3. 作为 user grant 与 capability grant 的归属根。

### OpenAppCredential

字段建议：

- `credential_code`
- `open_app_code`
- `app_id`
- `signature_version`
- `secret_material`
- `fingerprint`
- `last4`
- `status`
- `created_at`
- `updated_at`

职责：

1. 存储当前用于验签的 secret 材料。
2. 支持单活 key 轮换。
3. 负责一次性明文展示后的持久化形态。

1. 同一 `open-app` 第一版只允许一个 `active` credential。

### OpenAppUserGrant

字段建议：

- `grant_code`
- `open_app_code`
- `user_code`
- `created_at`
- `updated_at`

职责：

1. 明确记录某个 `open-app` 可以代理哪些用户。
2. 第一版只支持显式用户授权。

### OpenAppCapabilityGrant

字段建议：

- `grant_code`
- `open_app_code`
- `capability_code`
- `operation_code`
- `created_at`
- `updated_at`

职责：

1. 记录某个 `open-app` 可访问哪些业务能力与操作。
2. 授权粒度固定为 `capability + operation`。

### OpenApiNonceRecord

字段建议：

- `record_code`
- `app_id`
- `nonce`
- `request_timestamp`
- `expires_at`
- `created_at`

职责：

1. 做短 TTL 的 nonce 去重。
2. 拒绝同一 `appId + nonce` 的重复请求。

## HMAC 签名协议

### 版本

固定版本：

- `X-Tron-Signature-Version: TRON-HMAC-SHA256-V1`

### 请求头

正式 open-api 请求必须携带：

- `X-Tron-App-Id`
- `X-Tron-User-Code`
- `X-Tron-Timestamp`
- `X-Tron-Nonce`
- `X-Tron-Signature`
- `X-Tron-Signature-Version`

### Canonical String

第一版 canonical string 包含以下字段，顺序固定：

1. HTTP Method，转大写。
2. 规范化 path。
3. 规范化 query string。
4. request body 的 SHA-256 hash。
5. `appId`
6. `userCode`
7. `timestamp`
8. `nonce`

### 验签规则

1. 不接受 `Authorization: Bearer` 作为 open-api 正式调用方式。
2. `appId` 必须映射到 active `open-app` 与 active credential。
3. `timestamp` 必须处于允许偏差窗口内。
4. `nonce` 在有效时间窗内必须唯一。
5. 使用服务端保存的 secret 材料重算 HMAC。
6. signature 比较必须使用常量时间比较。
7. 任一失败都返回统一 Tron 响应体：

```json
{
  "code": "ERROR_CODE",
  "message": "error message",
  "data": {}
}
```

## 鉴权与授权流程

### Public Request Flow

1. 请求进入 `/open-api/v1/*`。
2. open-api middleware 先拒绝 Bearer 路径。
3. 读取 `appId`、`userCode`、timestamp、nonce、signature。
4. 加载 `open-app` 与当前 active credential。
5. 校验状态、签名版本、timestamp 窗口、nonce 唯一性、HMAC 签名。
6. 把路由映射成 `capability + operation`。
7. 校验：
   - `open-app -> userCode` grant 是否存在。
   - `open-app -> capability/operation` grant 是否存在。
8. 用 `userCode` 装配 acting user 的 `RequestAuthContext`。
9. 继续进入具体 handler。

### 关键限制

1. open-api handler 不应再隐式依赖“只要有 auth 就放行”。
2. route 到 capability/operation 的映射要前置在 middleware 或显式 metadata 中，不在 handler 内散落。

## Capability Catalog V1

第一版只暴露一个业务 capability：

- `agent-chat`

建议操作如下：

- `session.read`
  - 读取 session groups
  - 读取消息列表
  - 读取 AGUI replay

- `session.write`
  - 创建 session
  - 更新 session 元数据

- `message.read`
  - 读取消息列表

- `message.write`
  - 发送消息

- `stream.consume`
  - 调用流式回复端点

### Route Mapping 原则

第一版要求每条公开路由映射到一个固定的 `capability + operation`，例如：

1. `GET /open-api/v1/chats/session-groups` -> `agent-chat / session.read`
2. `POST /open-api/v1/chats/sessions` -> `agent-chat / session.write`
3. `GET /open-api/v1/chats/sessions/{sessionCode}/messages` -> `agent-chat / message.read`
4. `POST /open-api/v1/chats/sessions/{sessionCode}/messages/stream` -> `agent-chat / stream.consume`

## 前端管理设计

### 路由位置

新增：

- `/settings/openapi`

理由：

1. 现有平台配置语义已统一收口到 `Settings`。
2. `open-app` 更接近平台接入配置，而非业务应用管理。

### 页面结构

`Settings -> OpenAPI` 下采用单主列表 + 详情子视图。

#### Open Apps 列表

展示：

- 名称
- `appId`
- 状态
- 已授权用户数
- 已授权能力数
- 最近轮换时间

操作：

- 创建
- 进入详情
- 停用 / 启用

#### 详情页

分三块：

1. `Overview`
   - 名称
   - 描述
   - `appId`
   - key 指纹 / last4
   - 状态
   - 最近轮换时间
   - 轮换 key 操作

2. `User Grants`
   - 已授权用户表格
   - 添加用户
   - 移除用户

3. `API Grants`
   - capability 卡片
   - 每个 capability 下的 operation 切换或勾选

### 一次性 appKey 展示

创建和轮换都使用确认弹窗：

1. 后端生成新 `appKey`。
2. 前端只在本次响应中拿到明文。
3. 页面显式提醒“只显示一次，请立即保存”。
4. 关闭后列表和详情只显示指纹，不再展示原文。

## 持久化设计

建议新增独立表：

1. `platform_open_apps`
2. `platform_open_app_credentials`
3. `platform_open_app_user_grants`
4. `platform_open_app_capability_grants`
5. `platform_open_api_nonces`

### 设计要求

1. 不把 `open-app` 塞进现有 `app_management_apps`。
2. 不复用平台变量表存储正式签名 secret。
3. 不只存 bcrypt hash。HMAC 验签需要服务端能获得原始 secret 或等价可逆材料。
4. secret 必须以封装或加密形态持久化。

## 配置设计

建议扩展 open-api 相关配置，至少包括：

- `signatureSkewSeconds`
- `nonceTtlSeconds`
- `signatureVersion`
- `secretSealKey` 或等价 master key 配置

如果要兼顾不同环境，允许通过 `.env` 或 `application.yaml` 注入，但不能退回到“仅明文变量展示遮罩”的旧模式。

## 测试与验收门禁

实现完成前，至少要满足以下测试覆盖。

### 管理接口

1. 创建 `open-app` 成功，并返回一次性明文 `appKey`。
2. 列表和详情不再返回明文 `appKey`，只返回指纹或脱敏值。
3. 更新、停用、启用成功。
4. 轮换 key 成功，新 key 明文只返回一次，旧 key 立即失效。
5. 添加和移除 `userCode` 授权成功。
6. 设置和读取 capability grants 成功。

### 鉴权

1. 正确 HMAC 请求成功。
2. Bearer 请求被拒绝。
3. 缺少必要头被拒绝。
4. 错误签名被拒绝。
5. 过期 timestamp 被拒绝。
6. 重复 nonce 被拒绝。
7. 被停用的 `open-app` 被拒绝。

### 授权

1. `open-app` 未授权该 `userCode` 时被拒绝。
2. `open-app` 未授权该 capability/operation 时被拒绝。
3. 同时满足 user grant 与 capability grant 时请求成功。

### 公开聊天能力

1. 现有 open-api chat 路由在新鉴权模型下可正常工作。
2. 对应 route 的 capability/operation 映射正确。
3. 不再存在“只要内部 JWT 合法就能走 open-api”的后门。

### 前端

1. `/settings/openapi` 可进入。
2. 列表、详情、授权操作、轮换操作可完成。
3. 一次性 key 展示交互正确。

### 命令门禁

1. 后端测试必须先走 `make be-test`。
2. 若需缩小问题范围，再使用直接 `cargo test --manifest-path tron-backend/Cargo.toml ...` 做 focused rerun。
3. 前端校验至少覆盖类型检查、页面访问和交互路径。

## 风险与注意事项

1. 当前 open-api handler 权限边界偏松，后续需要把授权前置，避免 handler 级遗漏。
2. 当前仓库里的 secret 处理模式不能直接复用到 HMAC key。
3. 轮换 key 后旧 key 立刻失效，会要求接入方自行安排切换窗口。第一版接受这个约束。
4. capability catalog 第一版由代码内置，未来新增 capability 时需要同步更新管理页展示与路由映射。

## 交付标准

满足以下条件后，第一版可视为完成：

1. 平台 `Settings` 下具备 `OpenAPI` 管理页。
2. 管理员可以完整管理 `open-app`、用户授权、API 授权、key 轮换。
3. 正式 open-api 调用只接受 `TRON-HMAC-SHA256-V1`。
4. 请求显式携带 `X-Tron-User-Code`，并经过 `open-app -> user` 与 `open-app -> capability/operation` 双授权。
5. 现有公开聊天接口迁移到新模型后通过完整测试。
6. 所有响应仍符合 Tron 统一响应体格式。
