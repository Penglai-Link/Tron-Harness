# Agent Framework Brainstorm

## Context

The backend is a Rust service with domain, application, adapter, and shared modules. It already has model management, variable management, skill management, app management, workspace management, and a shared event bus. The agent framework should reuse these boundaries.

The platform needs a simple backend agent framework for the platform main agent. Different workspaces, apps, and users may run agents concurrently, so every run must isolate runtime state. The framework must support model configuration, effective variables, effective skills, effective tools, code execution scope, and runtime events that future AG-UI consumers can consume.

## Selected Approach

Build a real internal framework kernel and implement the first production-capable agent type: `ReactAgent`.

The first version will include a real `ModelClient` implementation for OpenAI-compatible APIs and a real `ToolRegistry`. Test substitutes for `ModelClient` are allowed only in backend unit tests. The production framework must be able to call configured models through the model configuration frozen into the run context.

The first version will run in the backend process. It will not implement Docker runtime, external Codex runtime, AG-UI protocol conversion, HTTP API exposure, sensitive variable handling, or run history persistence.

## Alternatives Considered

Starting with fake-only model and tool implementations was rejected. It would prove the loop shape but not the production framework boundary.

Directly adding Docker or external agent runtime was rejected for this slice. Those runtimes change variable materialization, tool execution, and security boundaries. The first version should stabilize the in-process contract first.

Creating a second agent event bus was rejected. Agent events should use the unified backend event bus. AG-UI can later be implemented as a consumer that adapts agent events into the AG-UI protocol.

## Core Concepts

The backend will add an agent framework module with these concepts:

- `AgentKind`: identifies supported agent types. The first value is `React`.
- `ReactAgentBuilder`: constructs a `ReactAgent` with a model client, tool registry, event publisher, and defaults.
- `AgentRunRequest`: carries prompt, conversation identity, workspace identity, user identity, app identity, and execution scope input.
- `AgentRunContext`: freezes one run's model, variables, skills, tools, execution scope, messages, observations, and limits.
- `AgentModelConfig`: the model configuration snapshot used by `ModelClient`.
- `ModelClient`: real model client abstraction with OpenAI-compatible Chat Completions, Responses, and Embeddings support.
- `Tool`: executable tool abstraction.
- `ToolRegistry`: real registry of tool executors.
- `Event`: the unified backend event contract. `AgentEvent` is one event category within it.

## Conversation And Run Identity

`conversation_code` and `run_code` must remain separate.

`conversation_code` identifies a chat conversation or frontend thread. Future AG-UI streams should use it to connect all events for one visible conversation.

`run_code` identifies one agent execution inside a conversation. A single conversation can contain many runs. Runtime diagnostics, step ordering, retries, and failures use `run_code` to distinguish each execution.

The default stream key can be `conversation_code`. Each event should still include both `conversation_code` and `run_code`.

## Agent Run Context

`AgentRunContext` is a frozen snapshot for one run. It must not store database connections, event bus handles, real tool executors, or other shared runtime dependencies.

The context should include:

```rust
pub struct AgentRunContext {
    pub conversation_code: Option<String>,
    pub run_code: String,

    pub workspace_code: String,
    pub user_code: Option<String>,
    pub request_id: Option<String>,
    pub stream_key: Option<String>,

    pub agent_kind: AgentKind,
    pub model: AgentModelConfig,

    pub variables: EffectiveVariableSet,
    pub skills: EffectiveSkillSet,
    pub tools: EffectiveToolSet,

    pub execution_scope: AgentExecutionScope,
    pub runtime: AgentRuntimeDescriptor,

    pub limits: AgentRunLimits,
    pub step_index: u32,
    pub messages: Vec<AgentMessage>,
    pub observations: Vec<ToolObservation>,
    pub started_at: String,
}
```

`trace_id` is not needed in this version.

## Execution Scope

Some platform agents operate on code repositories. Others only work inside platform business data. Code scope must therefore be optional:

```rust
pub struct AgentExecutionScope {
    pub app_code: Option<String>,
    pub repository_code: Option<String>,
    pub worktree_path: Option<String>,
    pub branch_name: Option<String>,
    pub task_code: Option<String>,
}
```

`app_code` identifies the current project or application. `base_branch` is not part of the first version.

## Model Client

`ModelClient` is a production component. It uses the `AgentModelConfig` inside the current `AgentRunContext`; it must not query model configuration by itself during a run.

The first implementation should support:

- OpenAI-compatible Chat Completions API
- OpenAI Responses API
- OpenAI-compatible Embeddings API

The ReAct loop can use Chat Completions or Responses for text generation. Embeddings are included as a framework capability for later memory, retrieval, and RAG tools.

Backend unit tests may use a test substitute for `ModelClient`, but production code must not depend on a fake-only model path.

## Variables

Effective variables come from the platform variable management capability, not from system environment variables.

The first version does not distinguish sensitive and non-sensitive variables because the current variable management page does not expose that capability yet. The run context can store resolved values:

```rust
pub struct EffectiveVariable {
    pub variable_code: String,
    pub key: String,
    pub value: String,
    pub source: VariableSource,
}
```

`EffectiveVariableSet` is resolved before the run starts and then stays frozen for that run. Later versions can add sensitive variables, `value_ref`, Docker environment injection, and external-agent tool proxy behavior.

## Skills And Tools

Skill and tool are different concepts.

A skill is a configured capability definition. It contributes instructions and names the tools that belong to that capability:

```rust
pub struct EffectiveSkill {
    pub skill_code: String,
    pub name: String,
    pub description: String,
    pub instruction: Option<String>,
    pub tool_names: Vec<String>,
}
```

A tool is an executable function exposed to the model:

```rust
pub struct EffectiveTool {
    pub tool_name: String,
    pub description: String,
    pub input_schema: serde_json::Value,
    pub skill_code: Option<String>,
    pub required_variable_keys: Vec<String>,
}
```

Skills influence the system instruction and decision boundary. Tools define callable actions. `AgentRunContext.tools` stores the allowed tool snapshot for this run. `ToolRegistry` stores the real tool executors.

## Tool Registry

`ToolRegistry` is a production component:

```rust
pub struct ToolRegistry {
    tools: HashMap<String, Arc<dyn Tool>>,
}
```

The registry validates and looks up executable tools by name. A test can register test tools, but the registry itself must be real.

Tool execution should receive the run context:

```rust
pub trait Tool {
    fn name(&self) -> &str;

    async fn execute(
        &self,
        request: ToolRequest,
        context: &AgentRunContext,
    ) -> Result<ToolObservation, ToolError>;
}
```

If a tool has internal mutable state or shared resources, that tool implementation must handle synchronization internally.

## React Agent Runtime

`ReactAgent` runs a bounded loop:

1. Create or receive `AgentRunContext`.
2. Publish `agent.run.started`.
3. Build the model input from the user prompt, effective skills, effective tools, effective variables, prior messages, and observations.
4. Publish `agent.model.requested`.
5. Call `ModelClient` using `context.model`.
6. Publish `agent.model.responded`.
7. If the model returns a tool call, validate that the tool exists in `context.tools`.
8. Publish `agent.tool.selected` and `agent.tool.started`.
9. Execute the tool through `ToolRegistry`.
10. Publish `agent.tool.completed` or `agent.tool.failed`.
11. Store the observation and publish `agent.observation.created`.
12. Continue until the model returns final output or a limit is reached.
13. Publish `agent.output.created` and `agent.run.completed` on success.
14. Publish `agent.run.failed` on failure.

## Unified Events

The backend should have one event system. `AgentEvent` is one event category or implementation under the unified `Event` concept. Agent runtime publishes agent events directly to the existing event bus.

The event flow is:

```text
ReactAgent -> EventBus -> observability consumer
                      -> audit consumer
                      -> future AG-UI adapter
```

Future AG-UI support should be implemented as an event bus consumer. It will filter agent events by `conversation_code`, `run_code`, and event name, then convert them into AG-UI protocol events.

First-version agent event names:

- `agent.run.started`
- `agent.run.completed`
- `agent.run.failed`
- `agent.step.started`
- `agent.step.completed`
- `agent.model.requested`
- `agent.model.responded`
- `agent.tool.selected`
- `agent.tool.started`
- `agent.tool.completed`
- `agent.tool.failed`
- `agent.observation.created`
- `agent.output.created`

Event fields should include:

- `conversation_code`
- `run_code`
- `workspace_code`
- `user_code`
- `request_id`
- `stream_key`
- `agent_kind`
- `runtime_kind`
- `step_index`
- `model_code`
- `tool_name`
- `skill_code`
- `app_code`
- `repository_code`
- `worktree_path`
- `branch_name`
- `task_code`
- `outcome`

The first version should still avoid placing full prompt text, completion text, or raw tool output in runtime events. Events are for runtime observation and future AG-UI adaptation, not full transcript storage.

## Concurrency Model

Agent definitions, `ModelClient`, and `ToolRegistry` can be shared dependencies. Each call to `run` creates an independent `AgentRunContext`.

Concurrent runs must not share `messages`, `observations`, `step_index`, or variable snapshots. Tool implementations that share resources must synchronize internally.

## Error Handling

The framework should define `AgentError` variants for invalid configuration, model failure, missing tool, unauthorized tool, tool failure, max step exhaustion, and unsupported runtime.

Failures must publish `agent.run.failed` before returning to the caller. Tool execution failures must publish `agent.tool.failed`.

## Test Strategy

Tests should cover:

- builder validation
- real `ToolRegistry` lookup and missing-tool behavior
- ReAct final answer without tools
- ReAct tool call followed by final answer
- max-step exhaustion
- model client request construction with frozen `AgentModelConfig`
- event ordering for the main lifecycle
- concurrent runs through one agent instance without context leakage

`ModelClient` test substitutes are allowed only in backend unit tests. The Makefile command for backend verification is `make be-test`.

## First Version Scope

Implement:

- `AgentKind`
- `AgentRunContext`
- `AgentExecutionScope`
- `AgentModelConfig`
- `EffectiveVariableSet`
- `EffectiveSkillSet`
- `EffectiveToolSet`
- real `ModelClient` with OpenAI-compatible Chat Completions, Responses, and Embeddings support
- `Tool` trait
- real `ToolRegistry`
- `ReactAgentBuilder`
- `ReactAgent`
- `AgentEvent` as part of the unified event model
- event publishing through the existing event bus
- unit-test-only model client substitute
- backend tests for ReAct flow, tool calls, events, concurrency, and limits

Do not implement in this version:

- Docker runtime
- external Codex runtime
- sensitive variable handling
- AG-UI protocol adapter
- run history persistence
- HTTP API wrapper

## Open Decisions

The first implementation will not expose HTTP routes. API design can follow after the platform decides how the main agent is invoked.

The first implementation will not persist run history. Event consumption can support observability and future AG-UI adaptation, while transcript storage can be designed separately.
