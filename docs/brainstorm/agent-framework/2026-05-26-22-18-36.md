# Agent Framework Brainstorm

## Context

The backend is a Rust service with clear domain, application, adapter, and shared modules. It already has model management, skill management, and a shared event bus with `Audit`, `Observe`, and `Agui` route classes. The first agent framework should reuse those boundaries instead of adding an external orchestration dependency.

The platform needs a simple framework for the main platform agent. Different workspaces and users may run agents concurrently, so each run must isolate runtime state. The framework must support model configuration, tool configuration, and internal events that cover the full runtime for later AG-UI support.

## Selected Approach

Use an internal framework kernel with a trait-based model client and test fake.

This version will implement a working `ReactAgent` over a `ModelClient` trait. It will not call a real model provider yet. Tests will use a fake model client and fake tools to prove runtime flow, event emission, and isolation. A later adapter can bridge the existing model configuration records to OpenAI-compatible HTTP calls without changing the agent core.

## Alternatives Considered

Direct HTTP model integration was rejected for this slice. It would couple the first framework version to provider details before the runtime contract is stable.

A type-only scaffold was rejected because it would not prove concurrency, tool execution, or event coverage.

An external agent orchestration library was rejected because the project already has Rust-native service boundaries and event infrastructure. A small internal kernel fits this codebase better.

## Design

The backend will add a new agent domain/application module with these core concepts:

- `AgentKind`: identifies supported agent types. The first value is `React`.
- `AgentBuilder` and `ReactAgentBuilder`: construct agents with model config, tool config, limits, and event publisher.
- `AgentRunRequest`: carries workspace code, user code, prompt, and optional run metadata.
- `AgentRunContext`: owns per-run state such as run id, step count, messages, selected tools, and event stream keys.
- `ModelClient`: async trait for model completion calls.
- `Tool`: async trait for configured tools.
- `ToolRegistry`: immutable registry cloned into each agent, with per-run tool lookup but no shared mutable execution state.
- `AgentEvent`: internal event enum covering run, step, model, tool, observation, and final output transitions.

`ReactAgent` will run a bounded loop:

1. Emit run started.
2. Build the model input from prompt and prior observations.
3. Ask the `ModelClient` for a decision.
4. If the decision requests a tool, emit tool events, execute the tool, store the observation, and continue.
5. If the decision returns a final answer, emit final output and run completed.
6. If limits or failures occur, emit failure and return an error.

## Event Coverage

Events will be internal first and mapped onto the existing event bus using `BusEventDraft::agui` or `BusEventDraft::observe`. Event names will be stable and namespaced:

- `agent.run.started`
- `agent.run.completed`
- `agent.run.failed`
- `agent.step.started`
- `agent.step.completed`
- `agent.model.requested`
- `agent.model.responded`
- `agent.tool.selected`
- `agent.tool.started`
- `agent.tool.completed`
- `agent.tool.failed`
- `agent.observation.created`
- `agent.output.created`

Sensitive prompt and completion text will not be placed in event bus payload fields because the current event bus rejects sensitive field names and should not carry raw private content. Events will carry metadata such as run code, agent kind, workspace code, step index, model code, tool name, and outcome.

## Concurrency Model

Agent definitions are immutable after construction. Each call to `run` creates a fresh `AgentRunContext`. The fake model client used in tests may use synchronization internally, but the framework will not require shared mutable state between runs.

Tools receive request data and return observations. Tool implementations must avoid storing per-run mutable state in the registry. If a future tool needs shared resources, it must guard them internally with explicit synchronization.

## Error Handling

The framework will define `AgentError` variants for invalid configuration, missing tools, model failure, tool failure, max step exhaustion, and canceled runs. The first version will not implement cancellation, but the error model will leave room for it.

Failures emit `agent.run.failed` before returning to the caller. Tool failures emit both tool failed and run failed unless future policy allows recoverable tool failures.

## Test Strategy

Tests will cover:

- builder validation for missing model client, missing model config, and invalid limits
- a final-answer run with no tools
- a ReAct run that selects a tool, observes the result, and then finishes
- max-step exhaustion
- concurrent runs using the same agent instance without state leakage
- event ordering for the main lifecycle

The Makefile command for verification is `make be-test`.

## Open Decisions

The first implementation will not expose HTTP routes. API design can follow after the platform decides how the main agent is invoked.

The first implementation will not persist run history. Events provide runtime observability, and persistence can be added once AG-UI and audit requirements are clearer.
