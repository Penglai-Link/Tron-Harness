# EliteForge Memory Dreaming Skill Brainstorm

## Context

Tron needs a repo-local agent skill source for memory dreaming development. The skill must be developed under `tron-skills/<skill-name>` so it is versioned with the project but not automatically loaded by the Tron backend or by Codex runtime discovery.

The implementation target is `tron-skills/eliteforge-memory-dreaming`. This stage is intentionally limited to the deterministic script foundation. The full skill prompting, memory extraction judgment, REM and Deep prompt contracts, Memory MCP writes, backend integration, and UI integration are deferred.

The detailed source design comes from the IntentForge memory dreaming work:

## Selected Approach

Build one CLI entry point with multiple internal Python modules.

The CLI entry remains easy for an agent to call:

```bash
python3 scripts/memory_dreaming.py init-run --provider codex ...
python3 scripts/memory_dreaming.py task-list --run-id ...
python3 scripts/memory_dreaming.py task-detail --run-id ... --task-id ...
```

Formal runs use the IntentForge workspace root `.intentforge-dreaming/` by default. Development, automated tests, and live Codex smoke runs pass `--artifact-root` to isolate artifacts in a dedicated test directory such as `/tmp/eliteforge-memory-dreaming`.

The implementation is split internally:

```text
tron-skills/eliteforge-memory-dreaming/
  SKILL.md
  agents/openai.yaml
  scripts/
    memory_dreaming.py
    memory_dreaming_lib/
      codex_provider.py
      artifacts.py
      tasks.py
      schemas.py
      report.py
      time_utils.py
    tests/
```

This keeps the command surface stable while keeping the code testable. It also leaves room for later provider support without turning the CLI file into a large script.

## Alternatives Considered

Putting the draft skill under `.agents/skills` or a configured `TRON_SKILLS_REGISTRY_ROOT/.agents/skills` was rejected because unfinished skills must not be auto-loaded by Tron agents.

Using `skills/<skill-name>` was considered, but it conflicts with the user's preference to reserve this work for Tron-specific skill development and does not clearly express that these are Tron project skill sources.

Building a complete skill prompt first was rejected for this slice. The current risk is not prompt quality; it is whether the artifact store, Codex session import, task state machine, temporary output handling, and final report generation are deterministic and testable.

Writing one large Python file was rejected because the state machine, provider reader, schema checks, and report generation need focused tests.

## Skill Identity

- name: `eliteforge-memory-dreaming`
- source path: `tron-skills/eliteforge-memory-dreaming`
- loading boundary: not copied to `.agents/skills` and not loaded by `TRON_SKILLS_REGISTRY_ROOT`
- first provider: `codex`
- formal artifact workspace root: `.intentforge-dreaming/`
- development and test artifact workspace root: caller-provided isolated directory, commonly under `/tmp/eliteforge-memory-dreaming`

Every CLI command that reads or writes Dreaming artifacts must accept `--artifact-root` as an override. When the option is omitted, the script resolves the artifact root to `.intentforge-dreaming/` under the current workspace. Automated tests and development smoke must always pass an isolated temporary directory.

## V1 Command Surface

The first script version implements the IntentForge V1 dreaming commands:

- `init-run`
- `task-list`
- `task-detail`
- `task-start`
- `task-complete`
- `task-fail`
- `task-retry`
- `status`
- `finalize-run`

The task states are only:

- `INIT`
- `RUNNING`
- `COMPLETED`
- `FAILED`

There is no `task-checkpoint`, `task-skip`, `claim-task`, `write-artifact`, or `register-session` in V1.

## Codex Provider

V1 supports only `provider=codex`.

The provider scans:

```text
~/.codex/sessions/**/*.jsonl
~/.codex/archived_sessions/*.jsonl
~/.codex/session_index.jsonl
```

The script should normalize Codex JSONL into a provider-neutral Dreaming Session Snapshot. CLI output must not print message bodies. Formal runs write working artifacts to `.intentforge-dreaming/`, matching the IntentForge design. Development live Codex smoke runs must pass an explicit non-repo artifact root such as `/tmp/eliteforge-memory-dreaming`, and those runtime artifacts must not be committed.

## Artifact Model

The artifact workspace follows the IntentForge logical design. Formal runs use `.intentforge-dreaming/` as the resolved artifact root:

```text
.intentforge-dreaming/
  runs/<dream-run-id>/
    dream-scope.json
    session-index.json
    tasks.json
    deep-governance.json
    dream-report.md
  sessions/<session-key>/
    snapshot.json
    segments/*.material.md
    segment-notes/*.notes.json
    session-summary.json
    light-memory-points.json
    rem-governance.json
```

When development or tests override the root, the same internal structure lives under `<artifact-root>/`.

For deterministic automated tests, `--artifact-root <artifact-root>` must point at a temporary directory created by the test runner.

For manual development live Codex smoke, the override root must be outside the repository:

```text
/tmp/eliteforge-memory-dreaming/<dream-run-id-or-test-run>/
```

`runs/<dream-run-id>/` records the current run, task state, scan decisions, Deep status, and final report. It must not copy session text.

`sessions/<session-key>/` stores reusable normalized session work material and analysis artifacts.

## IntentForge Compatibility

The original IntentForge design names `.intentforge-dreaming/` as the local workspace root. This Tron implementation preserves `.intentforge-dreaming/` as the formal default root. `--artifact-root` exists only as a development, test, and smoke-run override. The internal `runs/` and `sessions/` structure remains compatible with the source design in both modes.

The implementation must preserve these V1 decisions from the source design:

- `dream-run-id` format: `<created-at-utc-safe>-<provider>-<random6>`.
- `init-run` exposed inputs: provider, `timeRange.startedAfter`, `timeRange.endedBefore`, and `maxSessions`; scanning, reimport, resume, and segment budget decisions remain script-owned.
- scan decisions: `IMPORT_NEW`, `REUSE_COMPLETE`, `RESUME_INCOMPLETE`, `REIMPORT_CHANGED`, `SKIP`, and `FAILED`.
- command set: `init-run`, `task-list`, `task-detail`, `task-start`, `task-complete`, `task-fail`, `task-retry`, `status`, and `finalize-run`.
- task states: `INIT`, `RUNNING`, `COMPLETED`, and `FAILED`.
- task types: `SEGMENT_SUMMARY`, `SESSION_SUMMARY`, `LIGHT_MEMORY_POINTS`, `REM_GOVERN_MEMORY_POINT`, and `DEEP_MEMORY_GOVERNANCE`.
- `task-list` returns summaries only; `task-detail` returns the needed input refs, bounded preview, schema, and `tempOutputRef`; `task-complete` accepts only `runId` and `taskId`.
- `outputRef` stays internal to the script and is never supplied by the agent.
- `finalize-run` is deterministic, idempotent, does not call Memory MCP, and does not let the agent write `dream-report.md` directly.

## Snapshot Minimums

`snapshot.json` must keep the source design's top-level shape:

```text
schemaVersion
sessionKey
sourceManifest
session
preprocess
events[]
segments[]
stats
```

V1 may use a minimal validated schema, but it must preserve these boundaries:

- `sourceManifest` identifies provider, source session id/ref, source range, source hash, import time, and importing run id.
- `events[]` normalizes Codex JSONL into stable event order, timestamp, event type, role, text, tool, files, trust boundary, raw ref, hash, and redaction metadata where available.
- `segments[]` records segment id, event order range, event count, character count, token estimate, and segmentation reason.
- normalized event enum values must align with the source design where applicable, including user messages, assistant messages, tool calls/results/errors, system events, compaction, subagent, notification, task, and other.
- `segments/*.material.md` files are generated from the snapshot; `task-detail` may return a preview, but not inline full material.

## Task Flow

`init-run` creates a DreamRun, writes `dream-scope.json`, scans Codex sessions by time range and `maxSessions`, writes `session-index.json`, imports or reuses snapshots, materializes segment files, and creates initial tasks.

For each session, the planned task chain is:

```text
SEGMENT_SUMMARY -> SESSION_SUMMARY -> LIGHT_MEMORY_POINTS -> REM_GOVERN_MEMORY_POINT
```

After all sessions complete, the script creates or enables:

```text
DEEP_MEMORY_GOVERNANCE
```

`finalize-run` deterministically creates `dream-report.md` only after `status.canFinalize=true`.

For this script-only slice, REM and Deep remain part of the task graph but do not call Memory MCP. Their schemas should allow deterministic no-op or dry-run governance outputs so the state machine, validation, and final report can be tested before prompt quality and Memory MCP integration are designed.

If `init-run` imports no new sessions, the run still needs a Deep step or explicit Deep no-op artifact before `status.canFinalize=true`, matching the source design's requirement that empty session windows can still perform global maintenance.

## Temporary Output Boundary

Agent-generated task output must be written to the script-assigned `tempOutputRef` under the operating system temp directory.

`task-complete` reads only the task's recorded `tempOutputRef`, validates it, writes the internal official artifact, and advances the task. It must not accept arbitrary output paths or inline large JSON.

On schema validation failure, the task stays `RUNNING`, and the agent may correct `tempOutputRef` and call `task-complete` again.

## Validation Strategy

Tests should cover the script layer without relying on real model calls:

- Codex JSONL discovery and time-window filtering.
- Codex active and archived session discovery.
- `init-run` scan decisions for import, reuse, resume, changed reimport, skip, and failed import cases.
- Snapshot creation without printing message bodies to stdout.
- Snapshot top-level shape and normalized event enum mapping.
- Segment material generation.
- `INIT -> RUNNING -> COMPLETED` task flow.
- `RUNNING -> FAILED -> INIT -> RUNNING` retry flow.
- `task-complete` refusal before `task-start`.
- `tempOutputRef` schema validation and promotion to official artifacts.
- Downstream task creation.
- no-op or dry-run REM/Deep completion without Memory MCP.
- `status.canFinalize` blocking and ready states.
- Deterministic `dream-report.md` generation.

Tests should use local fixtures under the skill test directory and temporary workspaces. Real `~/.codex` data may be used for manual development smoke only, not for deterministic tests. Manual development smoke artifacts must be written outside the repository, preferably under `/tmp/eliteforge-memory-dreaming`, and must not be committed. Formal runtime artifacts use `.intentforge-dreaming/` and are still runtime artifacts, not source artifacts.

## Out Of Scope

- Full `SKILL.md` prompt design.
- Production prompt contracts for segment, session, Light, REM, or Deep analysis.
- Memory MCP reads or writes.
- Tron backend Skill Registry loading.
- Frontend UI.
- Multi-provider support.
- Direct migration from IntentForge Java code.
- Automatic writing of `ACTIVE` memory.

## Open Decisions Resolved

- The skill name is `eliteforge-memory-dreaming`.
- The project source directory is `tron-skills/eliteforge-memory-dreaming`.
- V1 provider is `codex`.
- V1 scans both active Codex sessions and archived Codex sessions only when `init-run --provider codex` is invoked explicitly.
- Formal runs use `.intentforge-dreaming/`; development tests and live smoke use an explicit non-repo artifact root such as `/tmp/eliteforge-memory-dreaming`.
- V1 uses one CLI entry point and multiple internal modules.
- This slice creates a stable script and tests before designing final skill prompts.

## Open Questions

- Whether the final implementation should include a small wrapper shell script in addition to the Python CLI.
- Whether manual smoke against live `~/.codex` should be included in the final evidence or kept as optional local verification only.
- Whether the eventual skill prompt should expose all commands directly or guide agents through a narrower happy-path sequence.
