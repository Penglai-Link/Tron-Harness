# MCP Management

## Context

Tron already has five adjacent foundations that this design should reuse instead of bypassing:

- platform settings pages under `/settings/*`
- workspace-scoped management pages under the authenticated shell
- internal-agent policy and assignment management in workspace `/agents`
- backend agent runtime with concrete `EffectiveTool` schemas and in-process `ToolRegistry` execution
- shared HTTP client profiles and authenticated API middleware

Repository scan also surfaced six implementation realities:

- current backend and frontend auth flows protect management APIs with the existing authenticated session contract
- current internal-agent tool policy resolves static platform tools from backend-owned catalog definitions
- runtime invocation materializes the effective tool list per run, then executes by tool name through the in-process registry
- current HTTP client configuration is app-profile based, not per-row request tuning
- platform singleton configuration today uses dedicated tables and repositories rather than one generic `platform_configs` store
- workspace inheritance works today for variables, models, skills, and system-agent policy, but those inheritance models are not interchangeable

This means the request should not be implemented as a generic config engine plus unconstrained workspace override model. The first version needs a narrower shape that fits current runtime, auth, and persistence boundaries.

## Requirement

Tron needs a first productized MCP management capability that:

- manages platform-owned remote MCP server definitions
- exposes one inbound MCP gateway endpoint for the variables capability
- lets each workspace enable or disable inherited platform MCP servers without changing the upstream connection definition
- lets each internal agent decide whether MCP access is disabled, inherited from all enabled workspace servers, or restricted to an explicit selected-server list
- injects the effective MCP tools into runtime as callable tools for the current run
- keeps `disable` and `delete` semantics distinct so operator intent remains clear
- aligns with current authenticated management APIs and current shared HTTP client configuration

The clarified first-version boundary is:

- platform owns all MCP server definitions
- workspace only controls inherited enable or disable state
- internal-agent assignment is by MCP server, not by individual discovered tool
- management APIs use current Tron authenticated API rules
- transport APIs follow MCP HTTP bearer-token and resource-server conventions
- per-server timeout and pool tuning, workspace-local server authoring, and permission matrices are deferred

## Selected Approach

Build the feature as one bounded `mcp-management` capability with four coordinated layers:

1. `Platform MCP Gateway`
   - one platform-managed singleton configuration that controls whether `/mcp/variables` is exposed
2. `Platform MCP Server Registry`
   - platform-owned remote MCP server definitions stored in dedicated persistence
3. `Workspace Effective MCP Server Policy`
   - current-workspace enable or disable state over inherited platform servers only
4. `Internal Agent MCP Access`
   - workspace-effective agent policy that resolves which enabled MCP servers are eligible for a run

Runtime then adds a fifth derived layer:

5. `Dynamic MCP Tool Materialization`
   - discover tools from the effective MCP servers for the current run, then materialize them as `mcp.<server_code>.<tool_name>`

The key design choices are:

- keep platform MCP server definitions platform-only in v1
- add a dedicated workspace page for effective inherited MCP servers instead of overloading variable inheritance or workspace agent rows
- keep internal-agent MCP assignment on the existing `/agents` page because the assignment belongs to agent policy, not to server CRUD
- assign MCP access by server, not by individual discovered tool, because remote tool sets are dynamic and per-tool persistence would go stale quickly
- keep `disable` and `delete` semantics separate:
  - `disable` preserves server definitions, workspace overrides, and agent assignments
  - `delete` removes the platform definition and cascades dependent workspace overrides, agent assignments, and connection-pool cache entries
- align server connection behavior with current shared HTTP client profiles rather than introducing row-level timeout or pool controls

This is intentionally narrower than a full inheritance-plus-marketplace design. It gives Tron one stable feature surface that fits the current repo and leaves the more flexible authoring and override model to a later version.

## Alternatives Considered

### Allow workspace-local MCP server creation and full parent override in v1

Rejected.

This combines definition ownership, secret handling, inheritance conflict rules, and runtime invalidation into one first-version slice. It also does not fit the current variable or system-agent inheritance semantics cleanly.

### Persist internal-agent assignment by discovered MCP tool code

Rejected.

Remote MCP tool sets can change without a schema migration or operator edit. Persisting individual discovered tool selections would create frequent stale references and require a second repair workflow.

### Register all MCP tools in the static platform `BusinessToolCatalog`

Rejected.

Those tools are runtime-discovered per server and per workspace. They do not fit the startup-time static catalog model that current platform tools use.

### Reuse the generic management auth pattern for the MCP transport endpoint without MCP-aware bearer conventions

Rejected.

The management API and the MCP transport surface have different clients and interoperability expectations. The transport endpoint should follow MCP HTTP bearer-token and resource-server conventions rather than pretending it is just another browser-facing admin API.

### Add per-server timeout, keepalive, pool, and session-limit fields in v1

Rejected.

Current HTTP client behavior is configured through shared app-level profiles. Introducing row-level connection tuning now would create configuration that does not map cleanly to existing infrastructure.

## Scope Boundary

### In Scope

- platform settings page for MCP gateway state and platform MCP server registry
- workspace page for effective inherited MCP servers with current-workspace enable or disable behavior
- internal-agent MCP access mode and selected-server assignment in workspace `/agents`
- dedicated persistence for platform gateway config, platform MCP servers, workspace server overrides, and agent selected-server assignments
- runtime discovery and materialization of MCP tools from effective servers
- delete and disable semantics for server lifecycle
- focused backend, frontend, and runtime tests for the bounded v1 capability

### Out Of Scope

- workspace-local MCP server creation
- workspace override of parent `url`, `headers`, or `auth` values
- permission-matrix enforcement beyond authenticated API access
- per-server timeout, pool, and transport tuning
- stdio transport
- secret-vault integration
- per-tool MCP permission assignment
- inbound MCP endpoints for modules other than variables

## Core Concepts

### Platform MCP Gateway Config

One platform singleton controls whether the inbound variables MCP endpoint is available.

V1 fields:

- `gatewayEnabled`
- `variablesEndpointEnabled`
- audit timestamps

This config is platform-only and stored in dedicated persistence, following the existing singleton-config style already used elsewhere in the repo.

### Platform MCP Server

A platform-owned remote MCP server definition.

V1 fields:

- `serverCode`
- `name`
- `description`
- `url`
- `authKind`
- `authPayload`
- `headers`
- `enabled`
- audit timestamps

These definitions belong to the platform. A workspace may inherit them and locally disable them, but may not rewrite their connection definition in v1.

### Workspace Effective MCP Server Policy

Workspace policy resolves whether an inherited platform MCP server is effectively available in the current workspace.

Rules:

- if platform server is disabled, workspace cannot make it effectively enabled
- if platform server is enabled and workspace has no override, the effective server is enabled
- if platform server is enabled and workspace stores a local disable override, the effective server is disabled in that workspace only
- removing the local disable override restores inherited enabled behavior

### Internal Agent MCP Access

Each internal agent resolves MCP access independently from static platform-tool assignment.

V1 adds:

- `mcpAccessMode`
  - `disabled`
  - `all_enabled_servers`
  - `selected_servers`

If `selected_servers` is active, assignments persist by `(workspace_code, agent_code, server_code)`.

### Dynamic MCP Tool Materialization

Runtime discovery happens only after workspace-effective server resolution and internal-agent server filtering are complete.

For each selected effective server:

1. connect through shared HTTP client infrastructure
2. discover current remote MCP tools
3. materialize them as runtime tools named `mcp.<server_code>.<tool_name>`
4. append them to the run's effective tool set for the current invocation only

This keeps static platform tools and dynamic MCP tools separate while still making both callable through the same runtime.

## Surface Direction

### Platform Settings

- Route: `/settings/mcp-servers`
- Page content:
  - top gateway card for `/mcp/variables`
  - platform MCP server registry list and create/edit/delete flows

### Workspace MCP Servers

- Route: `/mcp-servers`
- Page content:
  - effective inherited server table
  - source ownership display
  - current-workspace enable or disable actions only

### Workspace Agents

- Route: `/agents`
- Page content:
  - internal-agent section extends current policy surface with MCP access mode
  - when `selected_servers` is active, expose selectable effective MCP servers from the current workspace

### Inbound Transport

- Route: `POST /mcp/variables`
- Behavior:
  - transport-specific auth and protocol behavior
  - no browser CRUD semantics
  - controlled by platform gateway config

## Runtime And Lifecycle Rules

- only future runs see newly enabled, disabled, added, or deleted MCP servers; active runs keep the tool snapshot they started with
- disabling a platform server removes it from future effective workspace visibility and future runtime tool discovery, but preserves workspace overrides and agent selected-server rows
- deleting a platform server cascades:
  - workspace server overrides
  - internal-agent selected-server assignments
  - cached pool entries for that server
- if a stale selected-server submission references a deleted server, the management API should reject it with a typed stale-assignment error

## Open Questions

- None. The first version is intentionally narrowed to avoid unresolved inheritance and runtime-policy ambiguity.
