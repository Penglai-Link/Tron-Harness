# 空间规则（SPACE_RULE）

有权威来源、适用于空间、项目、团队或仓库的长期协作规则。个人喜好、单次操作和源码中已有的普通事实不属于此类。

## 正文结构

`text` 使用普通 Markdown，按下面顺序表达。标签和可读内容跟随 `metadata.language`；以下为中文模板，不能原样保存占位文字。

```md
规则：<明确主体必须、应该或不得做什么>

权威来源：<规则制定者及其权限>

生效范围：<覆盖的团队、仓库、环境或流程>

适用条件：<何时影响后续操作>

例外：<例外条件及确认途径>

用法：<如何改变开发、测试、交付或沟通>

证据：<可追溯的规则出处>
```

## 类型字段

- `ruleOwner`：制定或维护规则的团队、空间或治理主体。
- `ruleSubject`：受约束的产物、流程或行为。
- `normativeLevel`：约束强度，例如 must、should、must_not。
- `sourceAuthority`：来源为什么有权制定规则。
- `exceptions`：已知例外或确认途径。
- `effectiveScope`：覆盖的仓库、环境或流程。

## 语义键与证据

`semanticKey` 的结构：

```text
space-rule:<范围编码>:<规则主题>:<约束强度>:<行为>
```

尖括号内容替换为稳定的小写 ASCII 段，保持同主题、同用途的键稳定；复核或补强时更新原记录，不靠改写措辞新建近似副本。

`sourceRefs` 要求：空间指令、批准的文档、治理决策或负责人的明确确认。单次工具输出不能制定规则。

## 合格示例

平台项目的架构变更必须引用已批准的决策，紧急修复按规范处理。

对应 `metadata.typeSpecific` 示例：

```json
{
  "ruleOwner": "平台项目维护者",
  "ruleSubject": "架构边界变更",
  "normativeLevel": "must",
  "sourceAuthority": "维护者批准的协作规范",
  "exceptions": "紧急修复按规范由负责人确认并补充记录",
  "effectiveScope": "平台项目架构变更"
}
```

这是局部内容示例，实际保存还需补全 SKILL.md 中的范围、标题、状态、语言和真实来源，不是完整工具调用。

## 不合格示例

“大家以后都遵守严格流程。”

原因：没有具体行为、有效范围或授权来源。
