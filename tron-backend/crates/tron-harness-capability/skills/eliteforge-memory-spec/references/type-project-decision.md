# 项目决策（PROJECT_DECISION）

已经确定的架构、接口、产品范围、命名、数据模型或交付策略。尚未批准的提案可以作为候选，不应成为生效决策；任务进度和个人偏好不属于此类。

## 正文结构

`text` 使用普通 Markdown，按下面顺序表达。标签和可读内容跟随 `metadata.language`；以下为中文模板，不能原样保存占位文字。

```md
决策：<先写结论，不先写讨论过程>

理由：<为什么采纳>

影响范围：<受影响的模块、接口或流程>

阶段与时效：<当前阶段、生效和替代条件>

适用条件：<未来哪些工作需要依赖该决策>

例外：<排除范围、替代决策或不确定性>

证据：<已接受决策的出处>
```

## 类型字段

- `decision`：一句话说明长期决策。
- `rationale`：采纳理由。
- `phase`：生命周期阶段，例如 prototype、first-version、production、deprecated。
- `temporalBoundary`：生效窗口、复核条件或被后续决策替代的条件。
- `affectedAreas`：非空数组，列出模块、接口、流程或文档。

## 语义键与证据

`semanticKey` 的结构：

```text
project-decision:<范围编码>:<项目>:<决策主题>:<阶段>
```

尖括号内容替换为稳定的小写 ASCII 段，保持同主题、同用途的键稳定；复核或补强时更新原记录，不靠改写措辞新建近似副本。

`sourceRefs` 要求：批准的规范、需求、设计评审、ADR、议题决议或负责人确认。讨论中的建议不能冒充已采纳决策。

同空间包含多个项目时保留项目段；原型和生产决策并存时用阶段区分。

## 合格示例

客户导出任务保存申请人、导出时间、筛选摘要和审批来源，后续资料修改不改变审计记录。

对应 `metadata.typeSpecific` 示例：

```json
{
  "decision": "客户导出任务保留不可变审计元数据",
  "rationale": "客户资料变化后仍需追溯导出行为",
  "phase": "production",
  "temporalBoundary": "直到后续批准的合规决策替代",
  "affectedAreas": [
    "客户导出",
    "审计日志"
  ]
}
```

这是局部内容示例，实际保存还需补全 SKILL.md 中的范围、标题、状态、语言和真实来源，不是完整工具调用。

## 不合格示例

“我们决定保持简单。”

原因：决策不具体，没有批准依据、阶段和影响范围。
